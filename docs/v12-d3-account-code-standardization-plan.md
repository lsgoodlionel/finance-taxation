# D3 科目编码国标化 · 方案

> 状态：**已完成**（第 1–6 步全部落地并验证）。
>
> ⚠️ **方案修订过一次**：初稿把改动当成「三处冲突项」，实施时发现目标编码被占用，
> 存在**编码占用链**，且牵出一个科目设置本身存疑的项。修订内容见第二节之二。
>
> 实施记录与两次踩坑见第八节。

## 一、为什么做：真正的收益不是「符合国标」

FT 现有三处编码与《企业会计准则——应用指南》的会计科目编号冲突：

| 现用编码 | 科目 | 国标编码 | 冲突点 |
|---|---|---|---|
| `6001c` | 主营业务成本 | `6401` | 与 `6001` 主营业务收入**前缀重叠** |
| `6301e`、`6301e01`…`6301e07` | 管理费用及其明细 | `6602` | 与 `6301` 营业外收入**前缀重叠** |
| `3131` | 本年利润 | `4103` | 不冲突，但非国标 |
| `3141` | 利润分配 | `4104` | 不冲突，但非国标 |

**名义收益是合规，实际收益是消灭一整类陷阱。**

因为前缀重叠，全仓每一处按前缀判定科目性质的地方都必须「先排除 `6001c` / `6301e`」。`reports/profit-accounts.ts` 的注释把这件事写得很清楚：

> 凡是按前缀判定的地方，`6001c` / `6301e` 必须先于 `6001` / `6301` 排除。

这是一条**靠人记得**的规则。漏排一次的后果是：主营业务成本被当成主营业务收入计入收入、管理费用被当成营业外收入——利润表直接反向。V8-P 修复的错账根因正是这一类。

国标化之后 `6401` 与 `6001`、`6602` 与 `6301` 不再有任何前缀关系，所有「先排除」的特例可以整体删掉。**这才是这次改动值得承担风险的理由。**

## 一之二、实施中发现：目标编码被占用（方案修订）

初稿假设 `6001c → 6401`、`6301e → 6602` 可以直接改。**写迁移时核对 049 的科目表，发现 `6401` 已被「财务费用」占用**——迁移会直接撞唯一约束失败。

对照《企业会计准则——应用指南》的会计科目编号，FT 的整个 6xxx 费用段都偏离国标：

| FT 编码 | FT 名称 | 国标编码 | 占用情况 |
|---|---|---|---|
| `6001c` | 主营业务成本 | `6401` | ⚠️ 被 FT 的财务费用占用 |
| `6101` | 税金及附加 | `6403` | 空闲 |
| `6201` | 销售费用 | `6601` | ⚠️ 被 FT 的「职工薪酬（成本）」占用 |
| `6301e` | 管理费用 | `6602` | 空闲 |
| `6401` | 财务费用 | `6603` | 空闲 |
| `6601` | 职工薪酬（成本） | — | **国标无此损益类科目** |

### 两个后果

**一、需要两阶段改写。** `6001c → 6401` 与 `6401 → 6603` 构成占用链，同一条 UPDATE 里做会在中间态撞唯一约束（PostgreSQL 的唯一约束默认 `NOT DEFERRABLE`，逐行即时检查）。必须先把全部受影响编码挪到临时值，再落到目标值。

**二、`6601 职工薪酬（成本）` 超出本次范围。** 国标里「应付职工薪酬」是负债类 `2211`，生产相关的职工薪酬应进生产成本/制造费用，没有这样一个损益类科目。**这是科目设置本身存疑，不是编码问题**——改编码解决不了它，而在不清楚它承载什么业务的情况下动它，风险远大于收益。

因此 `6201 销售费用 → 6601` 这一项**本次不做**：它的目标编码被一个需要单独判断的科目占着。

### 修订后的范围

| 改 | 不改 |
|---|---|
| `6001c → 6401`（配合 `6401 → 6603`） | `6201` 销售费用（目标编码被占，见上） |
| `6401 → 6603`，明细 `6401001/002 → 660301/660302` | `6601` 职工薪酬（科目设置存疑，独立立项） |
| `6301e → 6602`，明细 → `660201`…`660207` | `6001`、`6051`、`6111`、`6301`、`6711`、`6801` 等本就合规的 |
| `6101 → 6403`（无冲突，顺带做） | |
| `3131 → 4103`、`3141 → 4104` | |

**范围缩小是有代价的**：改完之后销售费用仍是非国标的 `6201`。但它与任何编码都不冲突、不产生前缀陷阱，留着的唯一代价是名义上不合规——远小于在不了解 `6601` 的前提下动它。

## 二、改动面（实测，非估计）

### 数据：8 张表 11 个列

用 `information_schema` 扫出全部存科目码的列，排除同名但无关的（`cost_centers.code`、`roles.code`、`tax_rates.code` 等）：

| 表 | 列 | 备注 |
|---|---|---|
| `account_templates` | `code`、`parent_code` | 新建公司的种子来源 |
| `accounts` | `code`、`parent_code`、**`path`** | `path` 是 ltree，由编码构成，**必须重建** |
| `ledger_entries` | `account_code` | 历史分录 |
| `voucher_lines` | `account_code` | |
| `voucher_draft_lines` | `account_code` | |
| `recurring_voucher_lines` | `account_code` | D1 新增 |
| `bank_accounts` | `account_code` | C3 新增 |
| `fixed_assets` | `asset_account_code`、`accumulated_account_code`、`expense_account_code` | C1 新增 |

`accounts.path`（ltree）是最容易漏的一处：它由科目编码拼成，编码变了必须整棵重建，否则科目树的父子关系全断。

**`accounts.id` 同样含编码**（`seed_company_accounts` 里是 `company_id || ':' || code`）。不改它会让 id 与 code 长期不一致——不影响功能（没有别的表按 id 引用科目），但会在排查时误导人。本次一并重建。

### 数据量（种子库实测）

- `ledger_entries` 中使用这些编码的分录：**4 条**（`6301e01` ×1、`6301e03` ×1、`6301e06` ×2）
- `accounts` 中受影响的科目：9 个编码 × 4 家公司 = **36 行**

**数据量不是难点。** 真正的难点在代码。

### 代码：40 个文件

- **非测试文件 22 个**：`chart-of-accounts.ts`、`profit-accounts.ts`、`balance-sheet-accounts.ts`、`account-semantics.ts`、`account-guard.ts`、`templates.ts`、`invoice-voucher.ts`、`travel-expense-rules.ts`、`close-plan.routes.ts`、`consistency.routes.ts`、`anomaly.routes.ts`、`boss-qa/routes.ts`、`assistant/routes.ts` 等
- **测试文件 18 个**：断言里写死了这些编码

## 三、迁移策略：一次性全量改写，不做双编码并存

两条路：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 一次性全量改写** | 一个迁移把 11 个列全部改掉，代码同步改，旧编码从此不存在 | **选它** |
| B. 双编码并存 | 加 `standard_code` 列，读路径两边都认，逐步切换 | 否决 |

**否决 B 的理由**：并存期内每一个读路径都要同时处理两套编码——而「每个读路径都要记得处理某件事」正是这次要消灭的问题本身。用一个更大的同类问题去解决它，只会让并存期无限延长（没人有动力做最后一步收尾）。

一次性改写的代价是**必须一次做对**。这由下面的防线保证。

## 四、防线

### 1. 迁移内自检：改完必须零残留

迁移末尾扫描全部 11 个列，发现任何旧编码就 `raise exception` 回滚。宁可迁移失败，不要一半新一半旧——那种状态下科目查不到、报表少数据，且很难回头查是哪一半。

### 2. 护栏测试：旧编码不得再出现在代码里

一条测试扫描 `apps/` 全部源码，断言不再出现 `6001c` / `6301e` / `3131` / `3141` 字面量（`chart-of-accounts.ts` 的映射表本身除外）。漏改一处，测试立刻红。

这与 `chart-parity.integration.test.ts` 是同一个思路：把「靠人记得」换成「机器记得」。

### 3. 前缀特例必须同步删除

改完编码而不删「先排除」的特例，等于白改——特例会继续存在，下一个人仍要记得它。护栏测试同时断言 `COST_ACCOUNT_PREFIX` / `NON_OPERATING_EXPENSE_PREFIX` 这两个常量已被移除。

### 4. 报表口径回归

`summary.test.ts`（17 项）、`profit-accounts.test.ts`、`fiscal-year-profit.test.ts` 是报表口径的既有防线，改完必须全绿且**断言值不变**——编码变了但每个科目的归类与金额不该变。任何一个数字变化都意味着分类错了。

## 五、分步实施

每步独立可验证、可单独回滚：

| 步骤 | 内容 | 验证 |
|---|---|---|
| 1 | 编码映射表（纯数据）+ 护栏测试（此时应为**红**） | ✅ 已落地；护栏实测报出 76 个待改文件 |
| 2 | 迁移：**两阶段**改写 11 个列 + `accounts.path` 与 `accounts.id` 重建 + 迁移内自检 | 集成测试；自检零残留 |
| 3 | 代码：`chart-of-accounts.ts` 与全部硬编码引用改新编码 | 类型检查 + 单测 |
| 4 | **删除前缀特例**（`6001c` / `6301e` 的先排除逻辑） | 报表口径测试断言值不变 |
| 5 | 测试文件里的编码断言同步更新 | 全量门禁 |
| 6 | 浏览器实测：科目树、利润表、资产负债表 | 人工确认科目树父子关系未断 |

全部完成。验证结果见第八节。

## 六、明确不做的

- **不改 `1002`、`2202`、`6001` 等本就符合国标的编码**。这次只动三处冲突项，动得越多回归面越大。
- **不提供「旧编码兼容读」**。理由见第三节。
- **不动 `account_type`**。业务语义标签与编码正交，D2/D1 已经证明按 `account_type` 驱动的规则不受编码变化影响——这也是这次改动风险可控的原因之一。

## 七、给评审的一句话

改动面 40 个文件听起来大，但其中 18 个是测试、22 个非测试文件里大部分只是把字符串常量换掉。**真正需要判断的只有一处：删掉前缀特例之后，报表分类是否仍然正确**——而那正好有 17 项既有测试守着，且断言值不该有任何变化。

### 结果

| 项 | 结果 |
|---|---|
| 迁移 070 | 通过，迁移内自检零残留 |
| 单测 | api 747 / web 127 全绿，**skipped 0**（护栏已转正） |
| 集成测试 | api 191、db 35、tools 60 全绿 |
| 报表口径断言 | **一个数字都没改** —— 这是方案第四节第 4 条的验收条件 |
| 浏览器实测 | 科目树父子关系完好；利润表分类正确；资产负债表本年利润按 `4103` 出 |

浏览器实测造了一组正好覆盖被删特例的分录（6001 收入 / 6301 营业外收入 / 6401 成本 /
660201 管理费用 / 660301 财务费用 / 6403 税金及附加 / 6801 所得税），利润表结果：

```
revenue 1,050,000   ← 6401 没被当成 6001 的延伸、660201 没被当成 6301 的延伸
cost      600,000   ← 删掉前缀特例后 6401 仍正确归入成本档
expenses   60,000   ← 不含所得税
incomeTax  80,000   ← 单列
grossProfit 450,000 = 1,050,000 - 600,000
totalProfit 390,000 = 450,000 - 60,000
netProfit   310,000 = 390,000 - 80,000
```

### 踩到的两个坑（同一个根因）

**占用链上的编码两头都在。** `6401` 既是财务费用的**旧码**，又是主营业务成本的
**新码**。任何「还有没有旧编码残留」的判据如果只看 `legacy` 列表，都会把正确落位
的 `6401` 报成残留。

这个坑踩了两次：

1. 迁移 070 的零残留自检误报 2 处，数据其实是对的；
2. 修完迁移后，源码护栏用同一个错判据把 12 个文件报成待改。

第二次之后才把判据提炼成 `RETIRED_CODES`（在 legacy 里**且不在** standard 里），
让 SQL 侧与 TS 侧共用一个概念，而不是各写一遍各错一遍。

**另一个坑**：`accounts.id` 是 `company_id || ':' || code`，编码互换时逐行 UPDATE
会在中途撞主键——id 必须和编码一样做两阶段。

### 顺带清掉的东西

删掉的不只是两个常量。四处读路径的 SQL 排除子句一并消失：

| 文件 | 删掉的东西 |
|---|---|
| `reports/profit-accounts.ts` | `NON_OPERATING_EXPENSE_PREFIX` 及其前置分支 |
| `analytics/routes.ts` | `REVENUE_EXCLUDED_PREFIXES` + `not like` 子句 |
| `tax-integration/consistency.routes.ts` | 同上 |
| `ai-agents/anomaly/anomaly.routes.ts` | 同上 |
| `ledger/close-plan.routes.ts` | 同上 |

`COST_ACCOUNT_PREFIX` 改名 `MAIN_BUSINESS_COST_PREFIX` 而非删除，**语义变了**：
它不再是「必须先排除的特例」，而是「利润表要把主营业务成本单列成 cost 档算毛利，
而 `category` 只到 `expense` 粒度」——一条正当的业务规则。

`account-code-guard.test.ts` 里那条「每条读路径都必须带排除表」的护栏，换成了守
**根因**的一条：科目表里不得存在「以收入前缀开头但不是收入」的编码。原来是 N 条
读路径各自记得补救，现在是从源头禁止产生需要补救的编码。

## 九、留给以后的

### `6201` 销售费用 / `6601` 职工薪酬（成本）

理由见第一节之二：`6601` 的科目设置本身存疑（国标里没有这样一个损益类科目），
需要独立立项，不是改编码能解决的。

### `4001` 生产成本 / `4101` 制造费用与国标撞号

实测科目树时发现的：国标里成本类是 `5001` 生产成本 / `5101` 制造费用，而 `4001`
是实收资本、`4101` 是盈余公积（所有者权益类）。FT 把成本类放在了 4xxx 段。

本次把 `3131 → 4103`、`3141 → 4104` 之后，4xxx 段里同时住着成本类（4001/4101）
和权益类（4103/4104）。

**当前不构成缺陷**：全仓没有任何按 `4` 前缀判定科目性质的代码（已 grep 确认），
分类一律走 `category` / `account_type`。但它是同一类陷阱的雏形，值得单独立项。
