# D3 科目编码国标化 · 方案

> 状态：**方案待评审，尚未实施**。本文给出改动面的实测数据、迁移策略与分步计划。

## 一、为什么做：真正的收益不是「符合国标」

FT 现有三处编码与《企业会计准则——应用指南》的会计科目编号冲突：

| 现用编码 | 科目 | 国标编码 | 冲突点 |
|---|---|---|---|
| `6001c` | 主营业务成本 | `6401` | 与 `6001` 主营业务收入**前缀重叠** |
| `6301e`、`6301e01`…`6301e07` | 管理费用及其明细 | `6602` | 与 `6301` 营业外收入**前缀重叠** |
| `3131` | 本年利润 | `4103` | 不冲突，但非国标 |
| `3141` | 利润分配 | `4104` | 不冲突，但非国标 |

**名义收益是合规，实际收益是消灭一整类陷阱。**

因为前缀重叠，全仓每一处按前缀判定科目性质的地方都必须「先排除 `6001c` / `6301e`」。`reports/profit-accounts.ts` 的注释把这件事写得很清楚：

> 凡是按前缀判定的地方，`6001c` / `6301e` 必须先于 `6001` / `6301` 排除。

这是一条**靠人记得**的规则。漏排一次的后果是：主营业务成本被当成主营业务收入计入收入、管理费用被当成营业外收入——利润表直接反向。V8-P 修复的错账根因正是这一类。

国标化之后 `6401` 与 `6001`、`6602` 与 `6301` 不再有任何前缀关系，所有「先排除」的特例可以整体删掉。**这才是这次改动值得承担风险的理由。**

## 二、改动面（实测，非估计）

### 数据：8 张表 11 个列

用 `information_schema` 扫出全部存科目码的列，排除同名但无关的（`cost_centers.code`、`roles.code`、`tax_rates.code` 等）：

| 表 | 列 | 备注 |
|---|---|---|
| `account_templates` | `code`、`parent_code` | 新建公司的种子来源 |
| `accounts` | `code`、`parent_code`、**`path`** | `path` 是 ltree，由编码构成，**必须重建** |
| `ledger_entries` | `account_code` | 历史分录 |
| `voucher_lines` | `account_code` | |
| `voucher_draft_lines` | `account_code` | |
| `recurring_voucher_lines` | `account_code` | D1 新增 |
| `bank_accounts` | `account_code` | C3 新增 |
| `fixed_assets` | `asset_account_code`、`accumulated_account_code`、`expense_account_code` | C1 新增 |

`accounts.path`（ltree）是最容易漏的一处：它由科目编码拼成，编码变了必须整棵重建，否则科目树的父子关系全断。

### 数据量（种子库实测）

- `ledger_entries` 中使用这些编码的分录：**4 条**（`6301e01` ×1、`6301e03` ×1、`6301e06` ×2）
- `accounts` 中受影响的科目：9 个编码 × 4 家公司 = **36 行**

**数据量不是难点。** 真正的难点在代码。

### 代码：40 个文件

- **非测试文件 22 个**：`chart-of-accounts.ts`、`profit-accounts.ts`、`balance-sheet-accounts.ts`、`account-semantics.ts`、`account-guard.ts`、`templates.ts`、`invoice-voucher.ts`、`travel-expense-rules.ts`、`close-plan.routes.ts`、`consistency.routes.ts`、`anomaly.routes.ts`、`boss-qa/routes.ts`、`assistant/routes.ts` 等
- **测试文件 18 个**：断言里写死了这些编码

## 三、迁移策略：一次性全量改写，不做双编码并存

两条路：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 一次性全量改写** | 一个迁移把 11 个列全部改掉，代码同步改，旧编码从此不存在 | **选它** |
| B. 双编码并存 | 加 `standard_code` 列，读路径两边都认，逐步切换 | 否决 |

**否决 B 的理由**：并存期内每一个读路径都要同时处理两套编码——而「每个读路径都要记得处理某件事」正是这次要消灭的问题本身。用一个更大的同类问题去解决它，只会让并存期无限延长（没人有动力做最后一步收尾）。

一次性改写的代价是**必须一次做对**。这由下面的防线保证。

## 四、防线

### 1. 迁移内自检：改完必须零残留

迁移末尾扫描全部 11 个列，发现任何旧编码就 `raise exception` 回滚。宁可迁移失败，不要一半新一半旧——那种状态下科目查不到、报表少数据，且很难回头查是哪一半。

### 2. 护栏测试：旧编码不得再出现在代码里

一条测试扫描 `apps/` 全部源码，断言不再出现 `6001c` / `6301e` / `3131` / `3141` 字面量（`chart-of-accounts.ts` 的映射表本身除外）。漏改一处，测试立刻红。

这与 `chart-parity.integration.test.ts` 是同一个思路：把「靠人记得」换成「机器记得」。

### 3. 前缀特例必须同步删除

改完编码而不删「先排除」的特例，等于白改——特例会继续存在，下一个人仍要记得它。护栏测试同时断言 `COST_ACCOUNT_PREFIX` / `NON_OPERATING_EXPENSE_PREFIX` 这两个常量已被移除。

### 4. 报表口径回归

`summary.test.ts`（17 项）、`profit-accounts.test.ts`、`fiscal-year-profit.test.ts` 是报表口径的既有防线，改完必须全绿且**断言值不变**——编码变了但每个科目的归类与金额不该变。任何一个数字变化都意味着分类错了。

## 五、分步实施

每步独立可验证、可单独回滚：

| 步骤 | 内容 | 验证 |
|---|---|---|
| 1 | 编码映射表（纯数据）+ 护栏测试（此时应为**红**） | 护栏测试如实报出 40 个文件 |
| 2 | 迁移：11 个列全量改写 + `accounts.path` 重建 + 迁移内自检 | 集成测试；自检零残留 |
| 3 | 代码：`chart-of-accounts.ts` 与全部硬编码引用改新编码 | 类型检查 + 单测 |
| 4 | **删除前缀特例**（`6001c` / `6301e` 的先排除逻辑） | 报表口径测试断言值不变 |
| 5 | 测试文件里的编码断言同步更新 | 全量门禁 |
| 6 | 浏览器实测：科目树、利润表、资产负债表 | 人工确认科目树父子关系未断 |

## 六、明确不做的

- **不改 `1002`、`2202`、`6001` 等本就符合国标的编码**。这次只动三处冲突项，动得越多回归面越大。
- **不提供「旧编码兼容读」**。理由见第三节。
- **不动 `account_type`**。业务语义标签与编码正交，D2/D1 已经证明按 `account_type` 驱动的规则不受编码变化影响——这也是这次改动风险可控的原因之一。

## 七、给评审的一句话

改动面 40 个文件听起来大，但其中 18 个是测试、22 个非测试文件里大部分只是把字符串常量换掉。**真正需要判断的只有一处：删掉前缀特例之后，报表分类是否仍然正确**——而那正好有 17 项既有测试守着，且断言值不该有任何变化。
