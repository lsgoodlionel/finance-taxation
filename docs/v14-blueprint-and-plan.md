# V14 蓝图与实施计划

> 四项都出自 V13 的**「明确不做的清单」**。当时排除它们各有理由，现在条件变了：
> 银企直连有了「不做实际验证」的约束、成本结转有了模拟数据来源。
>
> **推翻自己当初的判断要说清楚为什么** —— 否则那份清单就成了摆设。

---

## 一、四项的重新判断

| # | 项 | V13 当初为什么不做 | 现在为什么能做 |
|---|---|---|---|
| 1 | 银企直连 | 依赖各行协议与网银证书，无真实环境无法验证；协议差异大，抽象层写早必返工 | **约束改了**：只做框架与前台配置，不实际连接。返工风险转移到「适配器实现」那一层，而框架层的形状由多行协议的共性决定 |
| 2 | 会签/或签/加签/流程图 | 中小企业场景罕见，复杂度是串行流程的数倍 | **判断有误**：会签在采购、用印场景其实常见。当初的「罕见」是我按报销场景推断的，而审批流不只服务报销 |
| 3 | 成本结转 | 需要产量与在产品数据，FT 没有 | **数据来源解决了**：用公开的制造业成本结构造模拟数据 |
| 4 | 发票池自动匹配 | 误配代价高于省下的点击 | **这个判断仍然成立**，但结论要改：做成**建议**而不是自动挂载，误配代价就降到零 |

第 4 项值得单独说：我当初的推理没错（误配代价高），但由此得出「不做」是跳步了。
正确的结论是「不做自动挂载」，而**建议**保留了全部收益又没有误配风险。

## 二、逐项设计

### 1. 银企直连框架（不做实际验证）

**做什么**：一套能容纳各行差异的适配器框架 + 前台的证书与协议配置 + 指令生成与状态回写的完整链路，**只是不实际发起网络请求**。

**关键设计：适配器接口由协议共性倒推**

各行协议差异极大，但抽象层不是凭空设计的 —— 主流银企直连（工行、建行、招行、平安）在这几件事上是一致的：

```
1. 认证：证书 + 签名（RSA/SM2），差别在算法与证书格式
2. 单笔/批量付款：报文里都有「付款账号、收款账号、金额、用途」
3. 状态查询：异步回执，靠流水号关联
4. 余额与明细查询
```

所以适配器接口按这四件事定，**每家的差异落在实现里而不是接口上**。V14 只提供一个 `mock` 实现（返回固定成功），真实实现留给有对接需求时再写。

**证书不落库明文**。证书内容存文件路径或引用，密码走现有的 `integration_configs` 加密字段。前台只显示指纹与有效期，不回显内容 —— 这是最基本的密钥卫生。

**与已有 `banking/bank-api.ts` 的分界**

> 写这份蓝图时我说「V13 把银企直连列入明确不做」，动手时才发现**项目里已经有一套**
> —— `modules/banking/bank-api.ts`，250 行，做拉流水与代发工资。蓝图是在没查代码
> 的情况下写的，这一条判断有误。
>
> 但结论不用推翻，只需收窄：那套做的是**收**（拉流水）和**代发**，V14-A 做的是
> **对公付款指令**。两者不该合并：

| | `banking/bank-api.ts`（已有） | `bank-connect/`（V14-A） |
|---|---|---|
| 方向 | 主要是收（拉流水） | 付 |
| 认证 | apiKey / apiSecret | **证书 + 签名（RSA/SM2）** |
| 幂等 | 无 | `clientRef` 必需 |
| 状态 | 一次性返回 | 异步回执 + 轮询回写 |
| 配置基数 | 一家公司一条 | 一家公司**多个付款账号**，各自签约 |

幂等和状态回写是对公付款独有的：拉流水拉两次没关系，付款付两次是事故。
配置基数那一行决定了不能复用 `integration_configs`——那张表是
「公司 × 配置类型 = 一条」，一对多塞不进去。

**不自动改付款单状态**：银行说「已受理」不等于钱到账，mock 环境下说「成功」
更是假的。指令状态记在自己表上，付款单仍由出纳确认后标记已付。
把两者串成自动流程，等于让一个未验证的适配器直接改账。

**明确不做**：真实网络请求、任何一家银行的报文格式实现。

### 2. 会签 / 或签 / 动态加签

**这是审批引擎的重大改造。** V13 的注释里写着：

> 会签会把「当前步骤」从一个数字变成一个集合，这里每个函数都要改。

现在真要改了。设计：

| 模式 | 语义 | 数据形态 |
|---|---|---|
| 串行（现有） | 一个人批完到下一个 | `currentStepOrder` 一个数字 |
| **会签** | 该步骤的所有人都要批 | 一个步骤对应多个待办，全部完成才推进 |
| **或签** | 任一人批了就算过 | 一个步骤对应多个待办，任一完成即推进 |
| **加签** | 审批中临时加一个人 | 运行时往实例里插步骤 |

**关键决策：不改 `current_step_order`，而是引入「步骤参与人」表。**

把当前步骤从数字改成集合会波及每一处读写。更小的改动是：步骤序号仍是数字，
但**该步骤有几个参与人、各自批没批**记在新表 `approval_step_participants` 上。
推进条件由步骤的 `mode`（serial/all/any）决定。

这样 `applyApprovalAction` 的签名不变，只是多一个「本步骤是否已满足推进条件」的判断。

**流程图编辑器**：V13 说「表单足够，编辑器是独立产品的工作量」。这次做一个
**只读的流程图预览**（用已有的 Steps 组件横向展开，会签步骤显示为并列分支），
不做拖拽编辑 —— 编辑仍走表单。理由：可视化的价值主要在「看懂现有流程」，
而拖拽编辑的价值远小于其复杂度。

### 3. 成本结转（含模拟数据）

**做什么**：产量与在产品数据 + 生产成本归集 + 完工产品成本结转。

会计上的链路：

```
料工费归集 → 5001 生产成本
  ↓ 期末按约当产量分配
完工产品 → 1405 库存商品      （结转）
在产品   → 留在 5001 生产成本  （余额）
  ↓ 销售时
1405 库存商品 → 6401 主营业务成本
```

**关键设计：约当产量法**

在产品要按完工程度折成「相当于多少个完工品」才能分摊成本。这是成本会计的标准做法，
也是这个功能真正的技术内容 —— 其余都是记账。

```
约当产量 = 完工数量 + 在产品数量 × 完工程度
单位成本 = (期初在产品成本 + 本期归集成本) ÷ 约当产量
完工成本 = 单位成本 × 完工数量
期末在产品 = 单位成本 × 在产品约当量
```

**整数分 + 末项扫尾**，与折旧、外币分摊、费用分摊同一套 —— 完工成本与在产品成本
之和必须严格等于「期初 + 本期归集」，一分不差。

**模拟数据**：用服务器组装的成本结构（主板、CPU、内存、电源、机箱 + 人工 + 制造费用），
数量级参照公开的行业数据。数据放种子里，让功能在页面上有真实感。

### 4. 发票池自动匹配（做成建议，不自动挂）

**V13 的判断修正**：误配代价高于省下的点击 —— 这个推理对，但结论应该是
「不做自动挂载」而不是「不做匹配」。

**做成建议**：报销单填明细时，按金额、日期、供应商名给出候选发票，
**用户点一下选中**。省掉的是「在几百张票里翻找」，而不是「确认这张对不对」。

匹配打分（纯函数）：

```
金额完全相等      +50
金额差 ≤ 1 元     +30   （含税不含税的零头）
日期在费用日 ±7 天 +20
供应商名含关键词   +15
未被其他单据占用   必要条件（占用了直接不出现在候选里）
```

分数只用于**排序**，不设阈值自动选 —— 设阈值就等于自动挂载，绕回原来的问题。

## 三、实施顺序与批次

按用户指定的顺序，每项一个批次，各自可独立交付。

| 批次 | 内容 | 迁移 | 主要风险 |
|---|---|---|---|
| **V14-A** | 银企直连框架 + 证书配置前台 | 093 | 抽象层设计不当，将来接真银行时返工 |
| **V14-B** | 会签/或签/加签 + 流程图预览 | 094 | 波及现有审批引擎，回归风险最高 |
| **V14-C** | 成本结转 + 模拟数据 | 095 | 约当产量分配的舍入，与既有分摊口径要一致 |
| **V14-D** | 发票匹配建议 | 无 | 低。纯查询 + 打分，不改写任何数据 |

**B 的回归风险最高**：V13 的审批引擎有 17 条单测 + 10 条集成测试钉着，
改造时必须全绿才算通过 —— 那些用例正是为这一天准备的。

## 四、明确不做（V14 版）

| 不做 | 理由 |
|---|---|
| 任何一家银行的真实报文实现 | 用户明确要求「不做实际验证」。框架就位，实现留给有对接需求时 |
| 流程图拖拽编辑 | 可视化的价值在「看懂」，编辑走表单足够。拖拽是独立产品的工作量 |
| 分步骤成本法、标准成本法 | 约当产量法覆盖中小制造业的绝大多数场景。多一种方法就多一套分配逻辑与一套差异分析 |
| 发票自动挂载 | 误配代价高于收益。建议 + 人工确认保留全部收益且风险为零 |
| 委外加工、联产品副产品成本分摊 | 需要更复杂的产品结构模型，超出「让成本能结转」这个目标 |

## 五、护栏

延续 V13 的做法，V14 新增三条：

1. **适配器契约测试** —— `mock` 实现必须通过与真实实现相同的契约测试。将来接真银行时，
   那套测试就是验收标准。
2. **审批引擎回归护栏** —— V13 的 27 条审批测试在改造后必须全绿，一条不改。
   要改说明行为变了，而行为变了要有明确理由。
3. **成本结转平衡护栏** —— 完工成本 + 期末在产品 ≡ 期初 + 本期归集，一分不差。
   与试算平衡同级别的硬断言。
