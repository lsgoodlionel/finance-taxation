# V13 费控闭环：升级蓝图与实施计划

> 输入是一份六阶段的「报销与合同支付」业务蓝图（阶段零基础档案 → 阶段五归档审计）。
> 本文档做三件事：**逐条对照现状**、**给出导航与流程的优化方案**、**排出可独立交付的实施批次**。

---

## 一、先说结论

### 1.1 差的不是页面顺序，是三根支柱

对照下来，蓝图六阶段里 FT 已有的部分比预想的多，但缺口集中且致命。实测结果（种子库 + 源码双向核查，非凭印象）：

| 蓝图能力 | 现状 | 说明 |
|---|---|---|
| 会计科目体系 | ✅ 完整 | V12 已国标化，`account_type` 语义驱动 |
| 组织与人员档案 | ✅ | 公司/用户/角色/成本中心齐备 |
| 往来单位档案 | ✅ | C2 已补入口 |
| **费用标准** | ❌ **缺** | `payroll_policy` 是社保费率，**不是**差旅/招待标准 |
| **预算体系** | ❌ **缺** | 只有 `budget-variance` 报表接口，**预算金额靠 URL 传参**，无预算表、无占位、无冻结 |
| **审批流引擎** | ❌ **缺** | 只有三处硬编码 approve（凭证/结账/工资代发），无流程定义、无多级、无条件路由 |
| **申请单** | ❌ **缺** | 业务事项是通用容器，无「事前申请」语义 |
| **借款/备用金** | ❌ **缺** | 无单据、无冲销、无挂账 |
| **报销单** | ❌ **缺** | 费用直接进凭证，无「单据 → 审批 → 付款」链路 |
| 合同 | ⚠️ **浅** | 只有基本信息（编号/对方/金额/起止/状态），**无付款计划、无质保金、无累计已付** |
| 发票管理 | ✅ | 票据中心 + 查验 + OCR 提取 |
| 费用分摊 | ⚠️ | 有成本中心与外币分摊，无「一单多部门按比例拆」 |
| 银企直连/支付 | ❌ **缺** | `payroll_transfer_*` 是工资代发专用，非通用付款指令 |
| 凭证自动生成 | ✅ 完整 | `insertLedgerEntries` 唯一写入口 |
| 报表与分析 | ✅ | 报表中心 + 驾驶舱 |
| 归档与审计 | ✅ | 导出中心 + 审计日志 |

**三根缺失的支柱**：

1. **控制点**——预算与费用标准。没有它，「事前控制」无处落地，超标只能靠人眼。
2. **单据载体**——申请单 / 借款单 / 报销单。没有它，业务人员的动作没有承载对象，一切都得由会计代劳。
3. **流转机制**——可配置审批流引擎。没有它，多级审批、按金额分级、按类型路由全都做不了。

合同是第四块短板，但性质不同：它**已存在只是太浅**，补付款计划与质保金是扩展，不是新建。

### 1.2 不必推倒重来：三个现成接口

这个缺口看着大，但 FT 的既有结构恰好留了三个接口，V13 是**在骨架上长肉**，不是换骨架：

**接口一：业务事项的状态机已经是蓝图的骨架。**

```
draft → analyzed → awaiting_documents → awaiting_approval → posted → archived
                                                          ↘ blocked
```

对照蓝图：`draft/analyzed` 是阶段一（申请）、`awaiting_documents` 是阶段二（票据归集）、`awaiting_approval` 是阶段三（审批审核）、`posted` 是阶段四（支付核算）、`archived` 是阶段五（归档）。**六阶段与现有状态机一一对应**，不需要新造状态语言。

**接口二：`insertLedgerEntries` 是总账唯一写入口。**

报销单、付款单、借款冲销这些新单据最终都要落账。走这个唯一入口，就自动继承了借贷平衡校验、会计期间校验、审计留痕——V13 不需要为账务一致性重新做一遍保证。

**接口三：`workflow.view` / `workflow.manage` 权限键已在目录里，但没有任何菜单项使用它。**

这是历史上给审批流预留的位置。V13 用它，不需要动权限体系。

### 1.3 导航的真实问题：分组维度对财务对，对业务错

现有 7 组 21 项按**会计职能**分（录入 / 经营管理 / 财务核算 / 税务 / 风控 / 工具 / 系统）。

这对会计是对的——他们按职能找功能，「要开凭证 → 凭证中心」。**不要为了迁就业务人员把它打散**，那会毁掉 V12 攒下的核算体验。

问题在另一侧：**业务人员在 21 项里几乎无处落脚**。申请人要提报销、审批人要批单子，而导航给他们的只有「记一笔」和「我的一天」——「记一笔」是记账口径，不是报销口径。

所以答案不是重排一套导航，而是**沿 V7 已有的 guided/pro 双轨继续分岔**：

- **guided 轨升级为「业务轨」**：按业务时序组织（我要申请 → 我的单据 → 我的审批 → 我的报销记录），面向申请人与审批人；
- **pro 轨保持职能分组**，新增一个「费控」组承接预算/申请/报销/付款，面向财务；
- 两轨**同一份数据、同一套状态机**，只是入口与信息密度不同。

这让 V13 不必推翻 V7 的成果，而是把 V7 搭好的双轨真正用起来——V7 时 guided 轨只有「记一笔 + 经营报告」，一直没有足以撑起一条独立轨道的业务内容，V13 补的正是这部分。

## 二、六阶段逐条对照与优化

### 阶段零：系统初始化与基础档案配置

| 蓝图要求 | 现状 | V13 动作 |
|---|---|---|
| 组织架构与人员 | ✅ | — |
| 会计科目 | ✅ | — |
| 供应商/客户档案 | ✅ | — |
| **费用标准库** | ❌ | **新建**：按职级/城市/费用类型定义限额 |
| **预算体系** | ❌ | **新建**：按部门/科目/期间的预算表 + 占用台账 |
| **审批流预设** | ❌ | **新建**：流程定义 + 条件路由 |

**费用标准库的设计要点**（差旅住宿是最典型的场景）：

维度是「费用类型 × 职级 × 城市等级」，值是「单日限额 / 单次限额」。超标不是一律拒绝——现实中经常需要「超标可提交但走加签」，所以标准要带**处理策略**：`block`（禁止提交）/ `warn`（提示但放行）/ `escalate`（触发加签）。

这一条直接决定了阶段三「智能审核」能不能自动判超标，是整条链的地基。

**预算的关键设计：占用（encumbrance）与实际发生分离。**

会计上预算控制有三个数：`预算额 / 已占用 / 已实际发生`。申请通过时**占用**预算（钱还没花，但已经不能给别人用了），报销付款时把占用转为**实际发生**。只记实际发生数，就会出现「三个人各自申请 8 万，预算 10 万，全部通过，最后超支 14 万」。

这里遵循 FT 一贯的**差额不凑平原则**：预算表里 `已占用 + 已发生 > 预算额` 时照实显示超支数并指出成因（哪几张单占的），不做任何自动平账。

### 阶段一：事前申请、合同签订与预算占位

| 蓝图要求 | 现状 | V13 动作 |
|---|---|---|
| 发起申请单（出差/采购/用款） | ❌ | **新建** `requests` 单据 |
| 预算校验与占位 | ❌ | **新建**，随申请单落地 |
| 合同管理与签订 | ⚠️ 浅 | **扩展**：付款计划、质保金、累计已付 |
| 借款/备用金申请 | ❌ | **新建** `advances` 单据 |

**申请单与业务事项的关系——这是最容易做错的地方。**

不要把申请单做成 `business_events` 的一个 `type`。业务事项是「已经发生的经营事实」，申请单是「尚未发生的意图」，两者的生命周期、校验规则、可编辑性都不同。正确关系是：**申请单审批通过后派生一条业务事项**，事项再往下走票据归集与核算。申请单保留自己的表与状态机，与事项之间是一对一或一对多的引用。

**借款的会计处理**：借款付款时借「其他应收款-备用金」贷「银行存款」；报销核销时用报销金额冲减该科目，多退少补。`1221 其他应收款` 已在科目表中，`account_type` 是 `asset_receivable`，**核销逻辑可直接复用 V12-D2 已做的往来核销机制**，不需要新写一套。

**合同扩展的三个字段组**：

1. **付款计划**（`contract_payment_schedules`）：期次、约定日期、约定金额、比例、状态。这是阶段四「合同状态更新」的依据，也是资金计划的来源。
2. **质保金**：比例、金额、到期日、释放状态。质保金的实质是「合同总额的一部分延后支付」，必须在付款计划里作为独立一期，否则合同永远显示「未付清」。
3. **累计已付**：不存字段，**由付款单实时汇总**。存字段一定会与实际付款不一致——这是 V12 反复验证过的教训（存冗余汇总列必然漂移）。

### 阶段二：业务发生、发票归集与单据填报

| 蓝图要求 | 现状 | V13 动作 |
|---|---|---|
| 发票 OCR 与查验 | ✅ | 复用 |
| 自动填单 | ⚠️ 部分 | **接线**：票据 → 报销单明细 |
| 报销单 | ❌ | **新建** `reimbursements` |
| 关联借款冲销 | ❌ | **新建** |
| 费用分摊 | ⚠️ | **扩展**：一单多部门按比例/金额拆 |

**OCR 已有但没接到报销上**——这是 V12 收口小结里点名的「后端有能力、没入口」问题的**第五次**出现。前四次是 D4 税务字段、D5 外币录入、D1 成本中心、C2 往来单位。

按那条已经写进蓝图的可操作结论办：**功能做完后去种子库数那一列有几行非空**。V13 的每个批次验收都必须包含这一项，写进护栏测试而不是靠人记得。

**费用分摊的落点**：分摊结果最终要变成凭证的多行分录，每行带不同的成本中心。`voucher_lines` 已有 `cost_center_id`（D1 补的入口），分摊只需在报销单层面记录拆分比例，落账时展开成多行。**用整数分计算 + 末期扫尾**，与折旧、外币分摊同一套算法，不引入新的舍入口径。

### 阶段三：审批流与智能审核

| 蓝图要求 | 现状 | V13 动作 |
|---|---|---|
| 多级审批流 | ❌ | **新建**引擎 |
| 条件路由（金额/类型/部门） | ❌ | **新建** |
| 三单匹配（合同-发票-验收） | ❌ | **新建**校验 |
| 预算稽核 | ❌ | 随预算体系落地 |
| 票据合规校验 | ✅ 部分 | 复用查验 + **扩展**抬头/税号/重复报销 |
| 业务合理性（超标检查） | ❌ | 随费用标准落地 |

**审批流引擎的范围要卡住。** 全功能 BPM（会签、或签、加签、转办、跳转、驳回到任意节点）是个无底洞。V13 只做覆盖 90% 场景的最小集：

- **串行多级**（部门经理 → 财务 → 总经理）
- **按金额分级**（≤1 万到部门经理止，>1 万加总经理）
- **驳回到发起人**（不做驳回到任意中间节点——那需要完整的流程实例回溯，收益远小于复杂度）
- **抄送**

明确**不做**：会签/或签、动态加签、流程图可视化编辑器、跨流程跳转。

**智能审核的四类校验**，全部做成**纯函数 + 结构化结果**，与 FT 已有的 `risk/engine.ts` 风控引擎同构：

```
校验结果 = { level: 'block' | 'warn' | 'info', code, message, evidence }
```

`block` 拦截提交，`warn` 提示但允许提交（审批人可见），`info` 仅记录。**重复报销检测**是其中最有价值的一条：同一发票号在系统内二次出现直接 `block`——这是真金白银的漏洞，且判定确定性高，不会误伤。

### 阶段四：支付执行、核算与合同更新

| 蓝图要求 | 现状 | V13 动作 |
|---|---|---|
| 付款单 | ❌ | **新建** `payments` |
| 银企直连 | ❌ | **接口预留**，V13 不实做 |
| 合同状态与台账更新 | ❌ | **新建**：付款单回写付款计划 |
| 质保金管理 | ❌ | 随合同扩展落地 |
| 自动生成凭证 | ✅ | 复用 `insertLedgerEntries` |

**银企直连 V13 不实做**，理由充分：它依赖具体银行的接口协议与企业的网银证书，无法在没有真实银行环境的情况下验证；而且各行协议差异极大，抽象层写早了必定返工。V13 只做到**生成付款指令并导出为银行可导入的格式**（这是中小企业实际的主流做法），把直连留给有真实对接需求时再做。这一点必须明说，不能让「银企直连」在蓝图里显示为已完成。

**自动生成的凭证一律 draft。** 这是 FT 从折旧、红冲、定期凭证、增值税结转、期末调汇一路贯彻的原则，报销与付款凭证没有理由破例。会计必须看一眼再过账。

### 阶段五：分析、归档与审计

| 蓝图要求 | 现状 | V13 动作 |
|---|---|---|
| 费用分析报表 | ⚠️ | **扩展**：按部门/类型/人员的费用分析 |
| 预算执行分析 | ⚠️ 接口在但无数据源 | 随预算体系接通 |
| 电子归档 | ✅ | 复用导出中心 |
| 审计追踪 | ✅ | 复用审计日志 |

现有 `budget-variance` 接口的预算金额靠 URL 传参——**接口是对的，缺的是数据源**。预算表落地后把它接上即可，不需要重写。

## 三、导航优化方案

### 3.1 pro 轨（财务）：7 组 21 项 → 8 组 26 项

新增 **GROUP_EXPENSE「费用与支付」** 组，插在 `GROUP_MGMT`（经营管理）之后、`GROUP_FINANCE`（财务核算）之前——**位置即语义**：费控在业务管理之后、账务核算之前，与实际业务时序一致。

```
GROUP_ENTRY    今天 / 记一笔 / 我的一天 / AI 财税助手 / 经营事项总线 / 董事长驾驶舱 / 任务中心
GROUP_MGMT     合同与往来 / 工资管理
GROUP_EXPENSE  ★ 申请与借款 / ★ 报销中心 / ★ 付款中心 / ★ 预算中心 / ★ 我的审批
GROUP_FINANCE  票据中心 / 凭证中心 / 总账中心 / 资产与往来 / 财务报表 / 导出与归档 / 银行余额调节表 / 单据中心
GROUP_TAX      税务中心
GROUP_RISK     研发辅助账 / 风险勾稽 / 审计日志
GROUP_TOOLS    制度库
GROUP_SYS      系统中心（★ 内含费用标准 / 审批流配置）
```

**费用标准与审批流配置放进系统中心而非独立菜单**：它们是**配置**不是**日常操作**，配置项进系统中心是 FT 既有约定（`SystemHubPage` 已承载科目表、往来单位等）。放在一级导航会让日常高频项被低频配置项稀释。

**「我的审批」放在费控组而非入口组**：虽然它是个人待办性质，但审批对象绝大多数是费控单据，放在一起用户找得到。入口组的「我的一天」仍然聚合所有待办（含审批），两者不冲突——**「我的一天」是聚合视图，「我的审批」是专项工作台**。

**权限键**：新增项复用已有的 `workflow.view` / `workflow.manage`（审批相关）；预算与报销需要新增 `budget.view` / `budget.manage` / `expense.view` / `expense.manage`。这是本次唯一需要扩展权限目录的地方。

**防膨胀护栏必须同步更新**：`nav-filter.ts` 里写死项数的断言会红，这是**设计如此**——它逼着每次导航变更都要有人显式确认。更新断言时把新的项数与分组一并写进注释。

### 3.2 guided 轨（业务）：2 项 → 5 项

现在 guided 轨只有「今天 / 记一笔 / 经营报告」，撑不起一条独立轨道。V13 补足：

```
今天          （已有，扩展：加待办卡片 —— 我的待批 / 我的待补票 / 我的被驳回）
我要申请      ★ 新增：出差 / 采购 / 用款 / 借款，四个入口一屏可选
我的单据      ★ 新增：我发起的全部单据 + 状态时间轴
我的审批      ★ 新增：待我审批（与 pro 轨同一页面，信息密度不同）
经营报告      （已有）
```

**「记一笔」从 guided 轨移除**——它是记账口径（选科目、填借贷），对业务人员是错的抽象。业务人员要的是「我出差花了 800 住宿费」，不是「借：管理费用-差旅费」。它保留在 pro 轨。

这是本次导航优化中**最重要的一处判断**：V7 时把「记一笔」放进 guided 轨，是因为当时没有别的业务入口可放。现在有了，就该把位置还给正确的抽象。

### 3.3 现有页面的内容与顺序调整

**合同页（`/contracts`）**——现在是「列表 / 看板」两视图，详情抽屉里是元数据 + 关联事项 + 时间轴。加两块：

- 抽屉内新增**付款计划表**（期次/日期/金额/状态/已付），位置在元数据之下、关联事项之上——**先看钱怎么付，再看关联了什么**；
- 列表新增**「本月应付」筛选**，让出纳能直接找出该付的合同。

**票据中心（`/bills`）**——现在票据是终点（查验完就完了）。加**「转报销单」动作**，让票据成为报销的起点。这是「后端有能力、没入口」的第五次修复。

**经营事项总线（`/events`）**——现在三个 Tab：看进展 / 传票据 / 问 AI。事项详情加**「来源单据」区块**：如果这条事项由申请单派生，显示申请单号与审批链路。不加新 Tab，避免总线页继续膨胀。

## 五、明确不做的清单

写下来是为了防止实施中范围蔓延。每一条都有理由：

| 不做 | 理由 |
|---|---|
| 银企直连实做 | 依赖真实银行环境与证书，无法验证；各行协议差异大，抽象层写早必返工。只做指令导出 |
| 会签 / 或签 / 动态加签 | 中小企业场景罕见，复杂度是串行流程的数倍 |
| 流程图可视化编辑器 | 表单式配置足够覆盖目标场景，编辑器是独立产品的工作量 |
| 驳回到任意中间节点 | 需要完整流程实例回溯，收益远小于复杂度。只做驳回发起人 |
| 成本结转 | V12 蓝图已明确排除，需要产量与在产品数据 |
| 移动端原生应用 | Web 响应式已覆盖申请与审批两个主要移动场景 |
| 发票池自动匹配报销单 | OCR 提取 + 人工选择已够用；自动匹配的误配代价高于省下的点击 |

## 六、护栏

延续 V12 的做法：**把「靠人记得」换成「机器记得」**。V13 新增五条：

1. **入口存在性护栏**——每个新单据类型必须有对应的前端创建入口。测试方式：扫描 `nav-filter.ts` 与路由表，断言每个 `expense.*` 权限键都有可达路由。这是对「后端有能力、没入口」（已发生五次）的直接防御。
2. **种子数据非空护栏**——种子库必须为每类新单据播种至少一条，且关键关联列（预算引用、成本中心、审批实例）非空。这是把「做完功能后去种子库数那一列有几行非空」写成测试。
3. **预算占用一致性护栏**——`budget_encumbrances` 的占用合计必须等于关联单据的未结金额合计，不一致即失败。
4. **审批流终态护栏**——任何审批实例不得停在无后继的中间态；扫描所有实例，断言每个非终态实例都有待办人。
5. **导航项数断言更新**——`nav-filter.ts` 的防膨胀断言随每批次更新，不允许「顺手加一项」。

## 七、与既有蓝图的关系

- **V12（会计核算内核）**：V13 完全建立在其上。科目国标化、`account_type` 语义字段、`insertLedgerEntries` 唯一写入口、往来核销机制——四项都是 V13 的直接依赖。V13 **不修改** V12 的任何核算逻辑。
- **V7（双轨 UX）**：V13 是 V7 双轨的第一次实质性使用。V7 建好了轨道但 guided 轨一直缺业务内容，V13 把它填满。V13 **不修改** V7 的轨道切换机制。

一句话：**V12 让账算得对，V7 让人分得开，V13 让钱管得住。**
