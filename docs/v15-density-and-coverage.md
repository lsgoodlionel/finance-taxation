# V15：拖拽编辑、页面减负与前台入口审计

> 这一版没有新的业务能力，做的是三件让已有能力真正可用的事。
> 其中第三件的发现值得单独记：**「后端有能力、没入口」不是偶发，是结构性的**。

---

## 一、审批流拖拽编辑

### 做成什么形态是被数据模型决定的

审批流在模型上是**线性**的——V13 定的：条件路由全部表达在步骤的金额门槛上，
不做分支。引擎按 `required_step_orders` 升序推进，存不下「A 之后分两条路」。

所以拖拽编辑的正确形态是两件事：

1. 拖步骤调顺序
2. 拖审批人跨步骤移动

**不是自由连线的节点图。** 做成节点图，用户能连出一个分支，而保存时会被
悄悄拉直——那比没有编辑器更糟，因为他以为自己配好了。

真要做分支流程，那是引擎的改造（`applyApprovalAction` 要能表达条件跳转），
不是前端组件的事。

### 几条细节

- 抓手单独一个元素：整块可拖会让里面的输入框选不中文字
- 键盘也能拖（`KeyboardSensor`）：审批流配置是管理员做的事，而管理员里有不用鼠标的人
- **最后一个审批人不许拖走**：空步骤会让单据永久卡死，而拖动的人未必意识到自己搬空了一步
- 门槛递减提示但不拦：它在语义上合法（可能就想「大额才要部门经理，小额直接财务」）

## 二、页面减负

### 量出来的问题

| 指标 | 最严重的几页 |
|---|---|
| 常驻说明块（`<Alert>`） | 研发向导 9、增值税向导 7、成本结转 6、合同关闭 6 |
| 表格列数 | 报销 21、税率 20、工资 20、成本结转 17 |

### 两个共享原语，不是一页页手改

**`Explain`** —— 可折叠说明块，默认收起、按 key 记忆。

> 这个产品的说明文字是它的价值所在——「为什么这一步不能跳过」「写反了会怎么样」，
> 那些话对第一次用的人是关键的。但常驻在页面上之后，第二次之后的每一次都在挡路。
>
> **折叠解决的正是这个矛盾：内容一个字不删，只是默认不占位置。**
> 删掉说明去换清爽是把新手扔掉，而那批人正是这个产品要服务的。

`defaultOpen` 只给「不看会做错」的用（成本结转的三项完工程度）。滥用它等于没有折叠。

**`useColumnPreset`** —— 核心 / 全部列切换。

> 不做勾选式列设置：20 列给一个勾选框，等于把「哪几列重要」推给正因为不知道
> 才打开这一页的人。**默认值才是产品的观点。**

一个 key 都没对上时退回全部列——空表会被读成「没有数据」，那是最难查的一种错。
折起来的列数要显示出来，不显示等于假装表就这么宽。

### 顺带修掉的一个真问题

报销明细原来有一列「科目」让用户手填 `660203`。**填报销的人多数不是会计**——
他知道自己住了酒店，不知道住宿费该挂哪个科目。手填的后果不是填不出来，是填错。

现在按费用类型自动带出（`expense-account-map.ts`），手改的入口在行展开区。

**业务招待费单列 660204**：它的税前扣除口径与差旅费完全不同（只能按 60% 且
不超过收入的 5‰），混进差旅费要到汇算清缴才发现。`chart-of-accounts.ts` 的
注释里记着一次真实事故就是这么来的。

## 三、前台入口审计：结构性问题

### 数字（含一次自我修正）

第一遍审计报的是「**34 条孤儿**」。那个数字**偏高**：判定只做字面前缀比对，
而前端常把 URL 拼起来（`/api/tax-integration/${type}`），那种看不见。

把判定改成「字面前缀 **或** 末段这个有区分度的词」之后，真实缺口是 **7 条**。

> 中间还走过一次弯路：我先把回退写成「逐段砍尾巴」，结果 `/api/ledger` 这种
> 两段前缀哪里都能命中，缺口一下降到 1 条——**那是把没入口的说成有**，
> 比漏报严重得多，因为它让护栏静默失效。改成只认末段（且末段要有区分度）才准。

不过第一遍的结论没有错：**期初建账、试算平衡表、银行付款指令导出、年度结转、
增值税期末结转**这五个确实是后端做完、前台一个入口都没有——它们是这次审计
真正要找的东西，34 与 7 的差别只是噪音多少。

其中约十个是后端实现完整、带集成测试、前台一个入口都没有：

| 能力 | 后端版本 | 后果 |
|---|---|---|
| **期初建账** | V12-B4 | **新公司建不了账，整个系统用不起来** |
| **试算平衡表** | 早期 | 月结前的第一张表看不到 |
| **银行付款指令导出** | V13-C6 | 没接银企直连的公司无路可走 |
| 年度结转 | V12 | 年末必做 |
| 增值税期末结转 | V12 | 月度必做 |
| 申报文件导出（XML/CSV） | — | 报税必需 |
| 现金流预测 / 收入对比 | — | 分析类，不阻塞 |

### 我之前对这个问题的判断是错的

V12 数到五次、V13 第六次、V14 第七第八次——我一直当它是偶发的疏忽，
在蓝图里写「功能做完后去种子库数那一列有几行非空」这样的应对办法。

**做完审计才知道它是结构性的**：做完后端、测试全绿，就当这件事做完了。
而用户打开系统，那个能力等于不存在。靠「记得检查」防不住——V13 写了应对办法，
V14 我自己又犯两次。

### 所以做成护栏

`apps/api/src/routes/registry-frontend-coverage.test.ts`：
**新增路由而前台没有调用点时，测试失败。**

两份清单，区别很重要：

- `BACKEND_ONLY_ROUTES`：**不需要**入口（运维探针、开放 API 元数据），每条说明为什么
- `KNOWN_GAPS`：**需要但还没做**，不让测试失败，但**每次跑测试都打印出来**

「以后会做」不是登记进白名单的理由——那种情况属于第二份清单，
它会一直提醒还剩多少，而不是被静默吞掉。

判定用字符串包含，故意粗糙：会把动态拼接 URL 的误判成「没入口」，
进而被逼着登记——那正好。**宁可多问一句，不可漏放一个。**

### 本次补上的五个

- **期初建账**：借贷差额摆在最显眼处、不自动补平（补平会造出一笔没人认识的账，
  它会一直留在账上直到某次审计问起来）；后端的结构化错误码用出来，坏科目高亮到行
- **试算平衡表**：排在三大报表**之前**——三组合计不平意味着账本身有问题，
  而资产负债表照样出得来、只是错的。不平时指出是哪一组差多少，不笼统说「不平衡」
- **银行付款指令导出**：勾选付款单导出 CSV，与「发往银行」二选一

- **年度结转**：不做的后果不是报错，是第二年的利润表把第一年的利润也算进去
  ——那个错通常要到报税时才被发现。后端的两种拒绝（月份未结转 / 上年未结账）
  原文透给用户，它们的处理方式完全不同。
- **增值税期末结转**：五种结论里有三种「什么都不用做」（留抵、轧平、不适用），
  界面把它们讲成正常结果、用 info/success 而不是 warning——给留抵一个黄色
  感叹号会让人去找一个不存在的错误。

### 剩余 7 条

| 路由 | 判断 |
|---|---|
| `GET /api/analytics/cash-forecast` | 分析类，不阻塞日常记账 |
| `GET /api/analytics/revenue-comparison` | 同上 |
| `GET /api/runtime/tasks` `/tax` | 前端有自己的汇总口径 |
| `GET /api/settings/users` | 权限页有自己的取数 |
| `POST /api/banking/sync-statements` | 手工模式下走 CSV 导入 |
| `DELETE /api/settlement/settlements/:id` | 核销撤销，列表页只做了核销 |

都不卡住周期性业务。最值得补的是核销撤销——核销错了现在改不了。
