# 增值税税率适用政策映射表

> 这份文件先于代码。**直接改代码会变成猜政策**——税率适用是有法定口径的，
> 猜错的代价是客户按错的税率申报。
>
> 依据：《增值税暂行条例》及财税〔2016〕36 号附件一《营业税改征增值税试点实施办法》，
> 以及现行有效的税率调整文件（财税〔2018〕32 号、财政部税务总局海关总署公告 2019 年第 39 号）。

---

## 1. 现状与缺口

### 1.1 税率主数据是完整的

`tax_rates` 表里六档齐全，适用范围也写清楚了：

| code | 税率 | 适用范围 |
|------|------|----------|
| `vat_basic` | 13% | 销售货物、加工修理修配劳务、有形动产租赁、进口货物 |
| `vat_low` | 9% | 交通运输、邮政、基础电信、建筑、不动产租赁、销售不动产、转让土地使用权、农产品等 |
| `vat_service` | 6% | 现代服务、金融服务、生活服务、增值电信、销售无形资产 |
| `vat_property` | 5%（征收率） | 销售不动产、不动产经营租赁、劳务派遣差额征税等 |
| `vat_simplified` | 3%（征收率） | 一般纳税人选择简易计税的特定应税行为 |
| `vat_zero` | 0% | 出口货物、跨境应税行为适用零税率 |

税率沿革（17%→16%→13%、11%→10%→9%）也在库里，按业务发生日取。

### 1.2 缺口：没有「这笔业务该用哪一档」的判定

`modules/tax/rules.ts` 的 `resolveVatRate` 完全不查这张表：

```ts
export function resolveVatRate(profile: TaxpayerProfile, treatment: string): string {
  if (profile.taxpayerType === "small_scale" || ...) return "3";
  if (treatment.includes("简易")) return "3";
  return "13";          // ← 一般纳税人一律 13%
}
```

后果：**一家做咨询服务的公司（应适用 6%）会被按 13% 算税**，
多算一倍还多。税务专员在 V16 角色实验里报的就是这条。

### 1.3 更深的缺口：判定所需的信息本身不存在

要判定税率档位，至少需要知道这笔业务卖的是什么。而系统里：

| 需要的信息 | 现状 |
|------------|------|
| 公司主营行业 | **`companies` 表没有这个字段** |
| 事项的应税行为类别 | `business_events.type` 只有 `sales` / `procurement` / `expense` 等**记账口径**的分类，与税目无关 |
| 合同标的的税目 | 合同表没有税目字段 |

**这是本次工作的核心：不是改一个函数，是补一条从业务到税目的信息链。**

## 2. 税目分类的设计

### 2.1 为什么不能按 `business_events.type` 推

`type` 是**记账口径**的分类（这笔业务在账上怎么走），税率适用要的是
**税目口径**（这笔业务卖的是什么）。两者不是一回事：

- 一笔 `sales` 可能是卖货（13%）、卖服务（6%）、卖不动产（9%）
- 一笔 `procurement` 的进项税率取决于**对方**卖的是什么，与我方无关

拿记账分类去推税目，等于用一个维度回答另一个维度的问题。

### 2.2 引入「应税行为类别」

新增一层枚举，直接对应税法的应税行为分类：

| 枚举值 | 中文 | 默认税率档 | 法定依据 |
|--------|------|-----------|----------|
| `goods` | 销售货物 | `vat_basic` 13% | 条例第二条第一项 |
| `processing` | 加工修理修配劳务 | `vat_basic` 13% | 条例第二条第一项 |
| `tangible_lease` | 有形动产租赁 | `vat_basic` 13% | 36 号文附件一第十五条 |
| `transport` | 交通运输服务 | `vat_low` 9% | 财税〔2018〕32 号 |
| `postal` | 邮政服务 | `vat_low` 9% | 同上 |
| `basic_telecom` | 基础电信服务 | `vat_low` 9% | 同上 |
| `construction` | 建筑服务 | `vat_low` 9% | 同上 |
| `real_estate_lease` | 不动产租赁 | `vat_low` 9% | 同上 |
| `real_estate_sale` | 销售不动产 | `vat_low` 9% | 同上 |
| `land_use_right` | 转让土地使用权 | `vat_low` 9% | 同上 |
| `agricultural` | 农产品等 | `vat_low` 9% | 同上 |
| `modern_service` | 现代服务 | `vat_service` 6% | 36 号文附件一 |
| `financial_service` | 金融服务 | `vat_service` 6% | 同上 |
| `lifestyle_service` | 生活服务 | `vat_service` 6% | 同上 |
| `value_added_telecom` | 增值电信服务 | `vat_service` 6% | 同上 |
| `intangible_asset` | 销售无形资产 | `vat_service` 6% | 同上（土地使用权除外） |
| `export_zero_rated` | 出口 / 跨境零税率 | `vat_zero` 0% | 36 号文附件四 |

### 2.3 判定优先级

税率不是「查一张表」那么简单，有优先级：

```
1. 零税率（出口、跨境）                    → 0%
2. 小规模纳税人 / 一般纳税人简易计税        → 征收率 3%（或 5%，看具体情形）
3. 按应税行为类别取档                      → 13% / 9% / 6%
4. 类别未知                                → **不猜，报「待确认」**
```

**第 4 条是这次设计里最重要的一条。** 类别未知时给一个默认值（比如现在的 13%），
错误会静默地流进申报表。宁可让这笔业务在底稿上显示「税目待确认」，
逼用户去补——这与 V16 修增值税 `NaN` 时的口径一致：
**算不出就说算不出，不要编一个数。**

## 3. 分阶段落地

### 阶段一（本次做）：判定链路打通

1. `companies` 加 `default_taxable_category`——公司主营的应税行为类别，
   作为事项没有明确类别时的**兜底**，而不是唯一来源
2. `business_events` 加 `taxable_category`——这一笔业务的应税行为类别，
   可空（不是所有事项都涉税）
3. `resolveVatRate` 改为：类别 → 查 `tax_rates` 表取档 → 返回税率
4. 类别未知且公司也没配默认值时，**返回 null**，底稿显示「税目待确认」
   并把这笔排除在合计外（复用 V16 已有的 `incompleteTaxItemIds` 机制）

### 阶段二（另行排期）：录入侧

- 建事项时让用户选应税行为类别（按公司默认值预填）
- 合同上带税目，事项从合同继承

### 阶段三（另行排期）：企业所得税与附加税

企业所得税现在写死 25%，实际至少要考虑：

| 情形 | 税率 | 依据 |
|------|------|------|
| 一般企业 | 25% | 企业所得税法第四条 |
| 小型微利企业 | 5%（应纳税所得额 ≤ 300 万部分减按 25% 计入 × 20%） | 现行小微优惠政策 |
| 高新技术企业 | 15% | 企业所得税法第二十八条 |

还缺：弥补以前年度亏损、已预缴税额抵减、附加税（城建税 + 教育费附加 +
地方教育附加，以实缴增值税为计税依据）。

**这三块每一块都需要独立的政策核对，不在本次范围。**

---

## 4. 这次不做什么

- **不改税率主数据**：那张表是对的
- **不猜税目**：类别未知就说未知，不给默认值
- **不做企业所得税优惠与附加税**：需要独立排期与政策核对
- **不做录入界面**：先把判定链路打通，界面在阶段二

## 5. 阶段一的实现记录

### 5.1 改了什么

| 层 | 改动 |
|----|------|
| 迁移 101 | `companies.default_taxable_category`、`business_events.taxable_category`、`tax_items.taxable_category` |
| 判定 | 新增 `tax/taxable-category.ts`：类别 → 税率档（`tax_rates.code`），17 个类别、四级优先级 |
| 底稿 | `resolveVatRateCodeForItem` 接上类别；税目未确定的行不进合计，单列在 `unknownCategoryTaxItemIds` |
| 闸门 | 申报导出遇到「税目待确认」返回 409，与 V16 的「计税依据缺失」并列 |
| 传递 | 事项类别 → 税项映射 → 税项落库；种子给两家公司配了主营类别 |

### 5.2 写的时候被自己的护栏抓到两次

**一、把小规模指到了错误的档。** 我让 `small_scale` 返回 `vat_simplified`，
而税率主数据里小规模是 `vat_small`——两档按 `taxpayer_type` 区分，
且小规模那档带减征沿革（3% 减按 1%，2023-01-01 起）。
指错导致取不到税率、算出 0。**被既有的减征沿革测试抓住了**。

**二、拆文件后动态 import 失效。** 把纳税人档案子域拆成
`taxpayer-profile.routes.ts` 之后，一条集成测试的
`await import("./routes.js")` 取不到 `createTaxpayerProfile`——
tsc 查不到这个，是 V16 建的动态 import 护栏抓的。

体量护栏也起作用了：`tax/routes.ts` 涨到 1172 行超线，
按护栏的要求「先想能不能拆」——档案是个完整子域，拆出去后降到 1078。

### 5.3 一个仍然存在的限制

事项的类别目前**只能通过 API 或直接改库设置**，界面上还没有选择入口
（那是阶段二）。所以现阶段绝大多数业务走的是**公司默认类别**这条兜底路径。

对单一业务的公司这已经够用；混合业务的公司（既卖货又做服务）
仍需要阶段二才能逐笔标注。**这个限制要在阶段二完成前如实告诉用户**，
不能让人以为系统已经能按笔区分税目了。

## 6. 验收标准

1. 一家做现代服务的公司，一笔咨询收入按 **6%** 算，不是 13%
2. 一家卖货的公司，一笔销售收入按 **13%** 算
3. 建筑服务按 **9%**
4. 小规模纳税人一律按征收率，不看类别
5. **类别未知时不给数字**：底稿显示「税目待确认」，该笔不进合计，
   申报导出被拒（复用 V16 的 `incompleteTaxItemIds` 闸门）
6. 税率仍按**业务发生日**取——沿革不能因为这次改动失效
