# 角色模拟实验：给每个 agent 的统一作业说明

## 你在做什么

你要**扮演一个真实的企业成员**，在一套正在运行的财税系统里完成 10 件本职工作，
然后如实报告哪里好用、哪里别扭、哪里根本做不了。

**你不是在测试代码，你是在上班。** 遇到不顺手的地方，先问「一个真人会怎么办」，
而不是「这个接口的设计意图是什么」。

## 环境

- API：`http://127.0.0.1:33100`
- 前端：`http://127.0.0.1:55173`
- 所有账号密码：`V4-test-123456`
- 登录：`POST /api/auth/login` `{"username":"...","password":"..."}` → `accessToken`
- 后续请求带 `Authorization: Bearer <token>`

## 硬性纪律（违反会毁掉别人的实验）

其他 5 个 agent 正在**同一个数据库**上同时工作。所以：

1. **绝对不要** reset / seed 数据库，不要跑任何 `npm run v4:test:*` 命令
2. **绝对不要** 锁定或解锁会计期间（`/api/ledger/periods/*/lock|unlock`）——那会让别人过不了账
3. **绝对不要** 执行月末结转 / 年度结转 / 期末结转，除非你的角色任务明确包含它，
   且你在报告里标注「此操作影响全局」
4. 你自己造的数据一律带前缀 `[<你的角色代号>]`，例如 `[ACC]采购一批服务器`
5. 只删你自己建的东西

## 怎么做「页面操作」

两条腿走路，**两条都要走**：

1. **API 层**：用 `curl` 或 node 脚本走真实接口，验证业务逻辑与数据正确性
2. **页面层**：用 Playwright 打开真实页面，验证这件事**在界面上做不做得到**

页面层的脚本模板（放在 `/tmp/<你的代号>-<任务名>.mjs`，用 `npx playwright test` 或直接 node + playwright）：

```js
import { chromium } from "playwright";
const browser = await chromium.launch();
const page = await browser.newPage();
await page.goto("http://127.0.0.1:55173");
// 登录、点击、截图……
await browser.close();
```

仓库里已有可复用的登录 fixture：`tests/e2e/fixtures/auth.ts`、
API 客户端：`tests/e2e/helpers/api-client.ts`。可以照抄它们的做法。

**页面层最该回答的问题：这件事有没有入口？** 后端能做但前台点不到，
在这个项目里是反复出现的问题，你要专门盯它。

## 四个验证角度

每完成一件事，从这四个角度各写一句：

| 角度 | 你要回答的问题 |
|------|----------------|
| **操作便捷性** | 从登录到完成，点了几次？找得到吗？有没有多余步骤？ |
| **逻辑正确性** | 数字对不对？状态流转对不对？重复提交会怎样？ |
| **业务合理性** | 一个真的会计/出纳会认可这个流程吗？符合国内财税实务吗？ |
| **功能完整性** | 做到一半卡住了吗？缺什么才能真正干完这件事？ |

## 报告格式

写到 `docs/v16-role-simulation/reports/<你的代号>.md`，结构如下：

```markdown
# <角色中文名>（<账号>）操作实验报告

## 我是谁
一段话：这个岗位每天在干什么，最在意什么。

## 10 件事的结果

### 1. <任务名>
- **怎么做的**：具体路径（接口 / 页面点击）
- **结果**：成功 / 部分成功 / 做不了
- **便捷性**：
- **逻辑正确性**：
- **业务合理性**：
- **功能完整性**：

（重复 10 次）

## 发现的问题（按严重度排序）

| # | 严重度 | 问题 | 证据 | 我建议 |
|---|--------|------|------|--------|
| 1 | 阻断/高/中/低 | | 具体请求或页面 | |

## 一句话总结
站在这个岗位上，这套系统现在能不能用？缺什么？
```

## 严重度口径

- **阻断**：这件事根本做不了，或做出来的数是错的
- **高**：能做但要绕路，或结果会误导人
- **中**：别扭、多点几下、文案让人猜
- **低**：小瑕疵

## 最重要的一条

**不许编。** 每一条发现都要有证据：贴出请求与响应，或说清在哪个页面点了什么、看到了什么。
你没验证的事就写「未验证」。一份看起来漂亮但没做过的报告，比不做更糟。
