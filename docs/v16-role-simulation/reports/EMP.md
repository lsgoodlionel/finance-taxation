# 经办员工（v4_employee）操作实验报告

> 角色代号 `EMP`。账号 `v4_employee` / 角色 `role-employee` / 部门 **销售部** / 公司 `cmp-v4-tech`。
> 实验时间 2026-08-27，环境 API `127.0.0.1:33100`、前端 `127.0.0.1:55173`。
> 我造的数据都带 `[EMP]` 前缀。

---

## 我是谁

我是销售部的业务员。一年碰这套系统十来次，每次都是被迫的：出差回来要报销、签了合同要录、
采购要走申请、出发前要借备用金。**我不懂会计。**「凭证」「过账」「科目」「贷方」对我是天书。
我只想：把票贴上去、填个数、点提交、然后知道钱什么时候到我卡上。

我最在意三件事，按顺序：**钱什么时候到**、**我要不要再做点什么**、**别让我填我不懂的东西**。

---

## 10 件事的结果

### 1. 提一张差旅费报销单（含多张发票明细）

- **怎么做的**：登录 → 左侧「我要报销」→「填报销单」→ 填费用发生日 2026-08-20 → 三行明细
  （差旅-住宿 880、差旅-交通 1240、差旅-餐补 300）→「保存为草稿」→「提交审批」。
  实际请求：`POST /api/reimbursements` → 201，`reimbursementNo: RMB-202608-0002`，
  `totalCents: 242000`；随后 `POST /api/reimbursements/{id}/transition {"action":"submit"}` → 200，
  `status: "pending"`。
- **结果**：**成功**。这是这套系统里我最满意的一个界面。
- **便捷性**：登录后 3 次点击就到了填单页，表头只有「费用发生日 + 冲抵借款」两个字段，
  明细只有「费用类型 / 金额 / 说明 / 发票」四列。**没有让我选科目**——V15 那次改对了。
- **逻辑正确性**：合计 2,420.00 自动由明细算出，与我心算一致。重复提交被挡：
  再点一次返回 `409 {"error":"报销单当前是「pending」，不允许执行「submit」"}`。
- **业务合理性**：**缺一个「事由」**。整张单没有地方写「这趟为什么出差」，
  只有每行的「说明」。请求体里 `note: null`，因为界面上根本没有这个输入框。
  审批人拿到的是三行费用，看不到「北京展会」这四个字。另外**没有附件上传**——
  「找发票」只能从系统里已有的进项发票池挑，而我手上是手机里拍的酒店水单。
- **功能完整性**：能提交，但提交之后就断了（见第 2 条）。而且**超标提示被吞掉了**：
  后端返回了
  `{"level":"warn","findings":[{"code":"standard.overrun","message":"限额 300.00 元/天 × 1 天 = 300.00 元，实际 880.00 元，超标 580.00 元。"}]}`，
  而界面上只弹了一个绿色的「操作成功」。要看到这句话，得回列表把那一行展开。
  另外那个「× 1 天」是错的——我住了 2 晚，`数量` 字段默认 1 且藏在折叠区里，我不会去改。

### 2. 查我的报销单走到哪一步了、钱什么时候到

- **怎么做的**：「我要报销」→「我的报销」页签；展开单据行；试 `GET /api/approval/pending`；
  去「问 AI」问「我上周提的差旅报销单现在到哪一步了？大概什么时候能打到我卡上？」。
- **结果**：**做不了**。
- **便捷性**：页签标题写着「提过的报销单走到哪一步了」，但表格里能看到的只有一个
  `状态: 审批中` 标签，「操作」列是「—」。
- **逻辑正确性**：状态字段本身是对的，但它不回答任何一个我关心的问题。
- **业务合理性**：**没有「轮到谁了」，没有「预计什么时候到账」，没有任何提醒。**
  我唯一能做的是每天自己回来刷这一页。
- **功能完整性**：`GET /api/approval/pending` 对我是
  `403 {"error":"Forbidden","requiredPermission":"workflow.view"}`——我连自己单子的审批进度接口都没权限。
  「问 AI」也不行：我问进度，它回「已识别一条可落地的经营事项，建议直接创建」，
  并给了一个「一键处理」按钮，标题是我那句问话
  （*注：本环境的助手是 deterministic 测试桩，回答质量不作数；但「把问句当成待创建事项」这个形状是真的*）。
  **更糟的是第 2 条其实无解，原因见问题表 #1。**

### 3. 提一个采购申请

- **怎么做的**：「我要申请」→「发起申请」→ 选「采购申请」→ 填事由标题、详细事由、
  预计金额 18000、预计发生日 2026-09-05 →「保存为草稿」→「提交审批」。
  `POST /api/requests` → `REQ-202609-0001`；`transition {"action":"submit"}` → 200 `status: "pending"`。
- **结果**：**成功**（提交这一半）。
- **便捷性**：4 类申请用大按钮平铺（出差 / 采购 / 用款 / 其他），比下拉好。
  「详细事由」下面写「审批人主要看这一段决定批不批，写清楚能省掉一轮来回」——这句话写得非常好。
- **逻辑正确性**：金额、日期、类型都存对了（`requestType: "procurement"`, `amountCents: 1800000`）。
  重复提交同样 409。
- **业务合理性**：**「费用科目」是个自由文本框，placeholder 写着「例如 660203」。**
  这就是不该问我的东西。同一个产品里，报销单已经做到了「选费用类型，科目自动带出」
  （`expense-account-map.ts`），申请单却退回让我手打编码。我留空了，
  代价是 `/api/requests/:id/precheck` 没跑，预算校验直接没做。
- **功能完整性**：采购申请里**没有地方填「买什么、几台、单价、供应商」**，只有一个总金额。
  我把「3 台联想 ThinkPad E14」写进了「详细事由」里。审批人批的是一个 18000 的数字。

### 4. 借一笔备用金

- **怎么做的**：「我要申请」→「借款与备用金」页签。
- **结果**：**做不了（前台没有入口）**。
- **便捷性**：这个页签是**只读**的。表头「借了多少、还欠多少」，
  空态写「还没有借款记录」，**页面上没有任何「我要借款」按钮**。
  「发起申请」按钮只通向 出差/采购/用款/其他 四种申请单，不含借款。
- **逻辑正确性**：后端完全正常。我用 curl 建了一张：
  `POST /api/advances {"amountCents":500000,"purpose":"[EMP]9月上海展会备用金","expectedReturnDate":"2026-09-30"}`
  → `201`，`ADV-202609-0002`。建完之后它**出现在了那个页签里**（状态「草稿」），
  但那一行**连「操作」列都没有**——建出来也提交不了。
- **业务合理性**：系统自己的说明书（系统中心 → 关于系统 → 三、日常节奏）白纸黑字写着
  「每天 / 员工 / 提报销、提申请、**借备用金**」。写在手册里的日常动作，界面上做不了。
- **功能完整性**：`createAdvance` 在 `apps/web/src/lib/api-expense-control.ts:395` 定义了，
  **全前端没有任何一处调用它**（`grep -rn "createAdvance" apps/web/src/pages/` 无结果）。
  这是这个项目反复出现的「后端能做、前台点不到」，第九次。
  值得单独说：V15 加的护栏 `registry-frontend-coverage.test.ts` 没抓到它——
  因为它是**字符串包含**判定，而 `api-expense-control.ts` 里有 `"/api/advances"` 这个字面量，
  于是 `POST /api/advances` 被判成「有入口」。**护栏检查的是「字符串在不在前端」，
  不是「有没有人能点到」。**

### 5. 用备用金冲抵报销（多退少补）

- **怎么做的**：报销单表头有「冲抵借款」下拉。在我已有一张 `pending` 的 5,000 元借款单的前提下打开它。
- **结果**：**做不了**。
- **便捷性**：下拉展开是「暂无数据」，**没有一个字解释为什么**。
- **逻辑正确性**：读代码知道原因——`ReimbursementsPage.tsx:123`
  `setAdvances(advanceData.items.filter((item) => item.outstandingCents > 0))`，
  而 `outstandingCents` 取自**已过账**的 1221 分录（`advances/store.ts:316`）。
  借款要走完「提交 → 批准 → 出纳付款 → 会计过账」四步才会有余额。这四步没有一步是我能做的。
- **业务合理性**：这是**真的会出错钱**的地方。一个借了 5,000 出差的人回来填报销，
  看到「暂无数据」，只能选「不冲借款（直接付给我）」——于是他拿到全额报销款，
  账上那 5,000 还挂着。这个错要到催收备用金时才被发现。
- **功能完整性**：「多退少补」的算法本身设计得很漂亮（`reimbursements/voucher.ts` 的注释：
  有借款时一律贷 1221，多退少补由余额符号自然体现，不写 if/else）。
  **但我端到端一次也没跑通，因为员工侧根本走不到那一步。此项标记「未验证」。**

### 6. 录一条经营事项（签了合同）

- **怎么做的**：首页「记一笔」磁贴 → `/quick-entry` →「打字描述」→
  「[EMP]8月25日和上海智联网络签了一份年度技术服务合同，含税金额 12 万元，客户先付 30% 预付款 36000 元，已到我们招行账户。」
  →「下一步：帮我认出金额和日期」→ 选「卖东西收到钱」→ 改对方单位 →「确认记下这笔账」。
  `POST /api/events` → 201 `evt-1787823699698-db38e9bb`；`POST /api/events/{id}/analyze` → `generatedTasks: 3`。
- **结果**：**成功**。整个 10 件事里体验最好的一件。
- **便捷性**：3 步，文案全程说人话。收尾页写「已记下！接下来：财务会为这笔安排入账，**您不用再做别的**。」
  ——这一句正是我想听的。「这是笔什么账？」的选项也是业务语言：
  「日常花销（吃饭/招待/办公/房租水电）」「合同回款/合同收入」，没有一个科目名。
- **逻辑正确性**：三处不对。
  ① 「对方是谁」被自动填成了 **「先付」**（从「客户**先付** 30%」里截出来的），我不改就存错；
  ② 金额取了合同总额 120000，而实际到账是 36000——界面上没有区分这两个数的地方；
  ③ 「哪天发生的」渲染成 `08/25/2026`（美式 MM/DD/YYYY），全站其他地方都是 `2026-08-25`。
- **业务合理性**：标题被拼成「卖东西收到钱 · 上海智联网络科技有限公司」——
  给我看没问题，但会计在事项列表里看到的就是这行字。部门默认「综合」，
  而我在销售部（`/api/access/me` 里有 `departmentName: "销售部"`），没有带出来。
- **功能完整性**：提交后前端还发了一个 `POST /api/close/drafts/generate {"period":"2026-08"}`，
  对我返回 **403 `{"error":"Forbidden","requiredPermission":"ledger.post"}`**，被静默吞掉。
  也就是说：**同一个事项，财务的人录会自动生成凭证草稿，我录就不会**——而且没人会知道。

### 7. 查我自己名下有哪些待办

- **怎么做的**：找侧边栏（只有「今天 / 我要申请 / 我要报销 / 问 AI / 经营报告」5 项，没有待办）；
  首页「还有 26 件 →」→ `/inbox`；直接敲 `/tasks`。
- **结果**：**部分成功**（能看到，但看不出哪些是我的）。
- **便捷性**：**引导模式的导航里没有任何「我的待办」入口。**
  `guidedNavItems`（`nav-filter.ts:134`）里的「我的审批」因为我没有 `workflow.view` 被过滤掉，
  剩下 5 项都不是待办。`/tasks` 只能靠敲 URL 或从首页卡片跳。
- **逻辑正确性**：`/tasks` 列出 17 条，**没有「负责人」列，也没有「只看我的」筛选**。
  标题还大量重名（「经营事项执行主任务」×3、「核对资料完整性」×3），无法分辨。
  API 层 `GET /api/tasks?mine=true` 与不带参数返回**完全相同的 14 条**——
  `mine` 这个参数在 `/api/tasks` 上根本不存在（`tasks/routes.ts:61` 只解析
  `businessEventId` 和 `overdueOnly`），被静默忽略。而 `/api/reimbursements?mine=true`
  是生效的。同一个参数名在不同接口下行为不同。
- **业务合理性**：`/tasks` 的副标题是
  「任务中心 · 结果页：承接主入口已生成的事项、任务、单据、凭证或税务结果，
  适合查看、复核与导出，不建议作为业务起点。」——这是产品架构说明，不是给我看的。
- **功能完整性**：`/inbox`（我的一天）给我显示「75 今天待处理」「月度结账」按钮、
  「2026-08 申报到期：还有 4 个税种没申报」。我是销售，这些跟我一件都没关系。

### 8. 能不能查到同事的事项（预期：看不到）

- **怎么做的**：`GET /api/tasks`、`GET /api/reimbursements`（不带 `mine`）、`GET /api/events`。
- **结果**：**看得到，而且比预期严重得多。**
- **便捷性**：不需要任何技巧，去掉一个 query 参数就行。
- **逻辑正确性**：
  - 任务：`GET /api/tasks` 返回 14 条，其中 8 条 `ownerId: "usr-v4-manager"`。
    这个是**有意设计**的（`tasks/routes.ts:36 scopeTasks` = `ownerId 相同 或 assigneeDepartment 相同`），
    我和经理都在销售部。可以接受。
  - 报销：`GET /api/reimbursements` 返回了出纳的
    `{"reimbursementNo":"RMB-202608-0001","applicantUserId":"usr-v4-cashier","totalCents":120000,"note":"[CSH] 超付测试用报销单"}`，
    `GET /api/reimbursements/{id}` 也返回完整明细。**这条路径没有任何归属过滤**，
    只要 `expense.view` 就能读全公司所有人的报销单。
  - 更严重：`POST /api/reimbursements/{别人的id}/transition {"action":"submit"}` **返回 200**，
    我把出纳那张草稿单提交了。（*我已用一条 `update reimbursements set status='draft' where id=... and status='pending'`
    把它改回 draft——`transitionReimbursement` 只改这一个字段、无副作用，
    已确认 CSH 的单子现在仍是 `draft`。在此向 CSH 说明。*）
- **业务合理性**：系统自己的说明书（关于系统 → 二、谁能做什么）写着
  「员工 / 能做：提申请、借款、报销，看自己的单据 / **不能：看不到别人的报销**，进不了账务与税务」。
  **这一行有三处与实现不符**：看得到别人的报销、能改别人的报销、
  首页天天给我看公司利润表和待过账凭证。
  代码里 `access/ownership.ts` 的注释甚至专门论证过这件事
  （「同部门任意人能改彼此的报销单，在职责分离上说不过去……改别人的报销等于替他签字」），
  但 `canMutateOwned` 没有被 `transitionReimbursementRoute` 调用。
- **功能完整性**：`GET /api/events` 20 条我都能看，`ownerId` 全是我——
  这批数据的归属本身就没分开，无法据此判断事项的可见性边界，此项标记「未充分验证」。

### 9. 查费用标准：出差住宿能报多少钱一晚

- **怎么做的**：引导模式导航里找不到 → 敲 `/settings` → 页面顶部横幅
  「这是财务专业页面 · 系统中心……看不懂是正常的：这页平时由财务同事操作」→
  点「费控配置」→「费用标准」。
- **结果**：**部分成功**。
- **便捷性**：**从我的导航出发是 0 条路径**。只有敲 URL 或全局搜索才进得去，
  而且进去还要先读一段「这页不是给你的」。
- **逻辑正确性**：表格本身做得很好，说人话：
  「职级 M2 · 一线城市 / 600.00 元/每天 / **加签**」、「不限职级 · 不限城市 / 300.00 元/每天 / **提示**」，
  上面还写「同一类费用下，更具体的标准优先……每组第一条就是会被用上的那条」。
  API 一致：`GET /api/expense-standards` 返回 `limitCents: 60000` / `30000`。
- **业务合理性**：**我不知道我是不是 M2，也不知道北京算不算一线。**
  `/api/access/me` 里没有 `gradeCode`。所以看完这张表我还是不知道自己能报多少。
- **功能完整性**：这一页对我显示了「新增标准」和每行的「停用」按钮，
  但它们对我必然失败——`POST /api/expense-standards` 与 `PATCH /api/expense-standards/:id`
  都返回 `403 {"error":"Forbidden","requiredPermission":"expense.manage"}`。
  **最该出现标准的地方是填报销单的时候，那里一个字都没有**——我填了 880 元住宿，
  界面没拦也没提示（后端的 warn 见第 1 条，被吞了）。

### 10. 找给「不懂财务的人」看的操作指南

- **怎么做的**：报销中心右上角「本页指南」；`/knowledge` 制度库；
  系统中心 →「关于系统」→ 完整说明书。
- **结果**：**成功，而且质量很高**——但摆的位置不对。
- **便捷性**：「本页指南」按钮每页右上角都有，一次点击。这个设计是对的。
  但**完整说明书埋在「系统中心 → 关于系统」里**，也就是那个横幅写着「您一般不需要在这里改动什么」的页面。
- **逻辑正确性**：报销中心的指南结构是：适用人群「所有人」→「用之前要先有」→「怎么用」六步 →
  「关键字段怎么填」表格 →「做错了会怎样」。举一句原文：
  「说明：写『差旅』不如写『深圳客户拜访住宿 3 晚』——后者在事后查账时才有用。」
  这是真懂业务的人写的。
- **业务合理性**：即便如此，对一个真的不懂财务的人，指南里仍然大量出现
  「科目」「贷方」「凭证摘要」「税前扣除」「汇算清缴」「一线/二线」。
  制度库 `/knowledge` 是空的（0 条），所以公司自己的报销制度并不在系统里。
- **功能完整性**：完整说明书里 **14 行把 Markdown 的 `**` 原样显示出来了**，例如
  「`**这是最关键的一步。**` 把启用系统之前的账面余额一次性录进来……」、
  「`**不能记账**`（没有 ledger.post）」。而且说明书里的两条关键说法与实现不符（见问题表 #1、#3）。

## 一句话总结

**能提，不能办。**

这套系统给业务员做的「入口」部分是我见过做得相当好的——报销单不问我科目、
「记一笔」三步说人话、每页右上角的指南是真懂业务的人写的。
但它只做完了**递单子**这一半：我提的申请、报销、借款，
前台没有任何人能批准，配好的审批流根本没被调用，
于是它们全部停在「审批中」不动，而我在界面上看不到轮到谁、也不知道钱什么时候到。

站在这个岗位上，**现在还不能用**。缺的是三样：
① 审批侧的入口和与审批流引擎的接线（问题 #1、#2）；
② 单据归属与职责分离的落地——现在我能批自己的报销、能改同事的报销（问题 #3、#4）；
③ 借备用金的前台入口，以及冲抵功能在员工手里真的能用（问题 #5、#9）。

补完这三样之前，一个真实员工用它的结果是：他把单子提上去，然后打电话问财务
「我的报销你收到了吗」——而财务在系统里也找不到它。
