# V16 六角色操作实验：计划、过程与结果

> 环境：`finance-taxation-v4-test` 容器栈｜代码基线：`feat/p0-path-level-acceptance`
> 六份原始报告：[`reports/`](reports/)

---

## 1. 目标

前面 P0–P3 四轮做的都是**开发者视角的验证**：类型检查、单元测试、集成测试、E2E。
它们能回答「代码对不对」，回答不了另一个问题——

> **一个真人坐在这套系统前面，能不能把活干完？**

这两件事的差距在这个项目里出现过很多次。最典型的是凭证红冲：后端从 V12 就在，
手册和页面指南都写着「过错了用红冲」，而前台**根本没有那个按钮**。
所有测试全绿，因为测试调的是 API，没有人去点过页面。

（这次实验又抓到同一个 bug 的第二版——见 §5.1。）

四个验证角度：

| 角度 | 要回答的问题 | 开发者测试为什么答不了 |
|------|--------------|------------------------|
| **操作便捷性** | 找得到吗？点几次？有多余步骤吗？ | 测试直接调接口，不经过「找」这一步 |
| **逻辑正确性** | 数字对不对、状态流转对不对 | 覆盖得最好，作为交叉验证 |
| **业务合理性** | 一个真会计会认可这个流程吗？合规吗？ | 测试只验证「按代码设计工作」，不问设计对不对 |
| **功能完整性** | 干到一半卡住了吗？缺什么？ | 测试只覆盖已实现的路径，缺失的东西没有测试 |

## 2. 方法

### 2.1 为什么按角色而不是按功能模块

按模块测会沿着代码结构走，测出来的还是代码覆盖。
按**角色**测，路径由岗位职责决定——它横穿多个模块，也会在模块之间的缝隙卡住。
那些缝隙正是单模块测试看不见的地方。

**这一点被结果证实了**：25 个阻断级缺陷里，至少 3 个位于「两个模块都对、
它们之间没人管」的位置（重复凭证、审批流没接进业务单据、过账写两张表只放开一张）。

六个角色覆盖完整层级：

| 层级 | 角色 | 账号 | 画像 |
|------|------|------|------|
| 决策层 | 董事长 | `v4_chairman` | 不懂会计，只要结论，10 分钟看完 |
| 管理层 | 财务负责人 | `v4_manager` | 懂行，管口径与内控，对准确性负最终责任 |
| 执行层 | 会计 | `v4_accountant` | 系统用得最重，在意每天少点几百下 |
| 执行层 | 出纳 | `v4_cashier` | 管钱不管账，没有记账权（设计如此） |
| 专业层 | 税务专员 | `v4_tax` | 对政策敏感，税率口径错一处全盘皆错 |
| 末端 | 业务员工 | `v4_employee` | 一年用十几次，完全不懂会计术语 |

**最容易被忽略的是两头**：开发者自己最像会计，写出来的界面也最合会计的口味。
结果印证了这一点——董事长和员工各自撞到了别人碰不到的缺陷
（首页「批准」按钮的重复凭证、报销自批自付）。

### 2.2 两条腿走路

| 层 | 手段 | 回答什么 |
|----|------|----------|
| API 层 | curl / node 走真实接口 | 业务逻辑与数据正确性 |
| 页面层 | Playwright 打开真实页面 | **这件事在界面上做不做得到** |

### 2.3 并发纪律与反造假约束

6 个 agent 在同一个数据库上同时工作，纪律写在
[`AGENT-BRIEF.md`](AGENT-BRIEF.md)：不 reset 库、不锁期间、不做结转、
自造数据带角色前缀、只删自己建的。

反造假约束：

> **不许编。** 每条发现都要有证据：贴出请求与响应，或说清在哪个页面点了什么、
> 看到了什么。你没验证的事就写「未验证」。一份看起来漂亮但没做过的报告，比不做更糟。

这条有来历：就在上一轮，我自己写的 E2E 有四个断言是照直觉编的、从没跑过，
而清单上写着「已覆盖」。

## 3. 执行过程

1. 确认容器栈健康，并**验证容器代码是当前 HEAD**——用 P1 新增的
   `/api/events/:id/collaborators` 探测，区分「路由存在但事项不存在」
   （`Event not found`）与「路由不存在」（`Not Found`）
2. 写统一作业说明，6 个 agent 并行开工
3. 报告回收后，**逐条自己复现**再采信（见 §4.1）
4. 按「根因确定性 × 影响面」排序修复
5. 每个修复配一条测试，并**反向验证**（改回 bug 版本确认变红）

### 4.4 第二批修复（6 条）

| # | 缺陷 | 根因 | 修复 |
|---|------|------|------|
| 9 | **前台无法过账任何凭证** | `postVoucher()` 写死发空 body，而过账是高风险动作、要求终审人 ≠ 执行人。每次 400 `WORKFLOW_AUTHORIZATION_REQUIRED`，还以未翻译的英文弹出 | 加终审人选择器（单张 / 键盘 / 批量三个入口都接上）。名单由服务端按 `?permission=ledger.post` 过滤——前端按 roleId 自己判断等于把权限表复制一份 |
| 10 | **分析生成的凭证在前台是死结** | 落库即 `review_required` 且 `approvedAt` 为空。前端按 **status** 判：审核按钮只给 `draft`，过账按钮给 `review_required`——而过账要求 `approvedAt` 非空，点了必然 400。实验时卡了 5 张 | 判据改成 `approvedAt`。status 是粗粒度标记，`approvedAt` 才是「有没有人复核过」的事实 |
| 11 | **403 被渲染成「没有数据」** | 研发页显示「还没有研发项目」、风险页显示「0 条 · 全部已关闭 · 关闭率 0%」，而接口是 403。**给人看「一切正常」比给人看报错危险得多** | 两页都区分「空」与「读不到」，403 指明缺哪个权限，并主动否认「没有数据」这个解读 |
| 12 | **并发付款不幂等** | 幂等判断在事务**外面**，六个并发请求同时读到 `voucherId` 为空、同时通过。实测并发 6 次 confirm → 6 个不同凭证号；借款打款同形状 | 判断挪进事务并 `select ... for update`。付款与借款打款两处都修 |
| 13 | **出纳看不到任何应付信息** | 「本月应付」「付款单列表」「付款中心菜单」全挂在 `contracts.view` 上，而出纳没有这个权限。深链进去整页 403——那段代码的注释还写着「出纳每天要看的第一个东西」 | 给 `role-cashier` 加 `contracts.view`（只读）。记账权 `ledger.post` 仍然不给 |
| 14 | **税务专员做不了两件本职工作** | 缺 `rnd.view`（加计扣除归集）与 `risk.view`（税务风险）——而风险引擎里的规则全是税务规则 | 补这两个读权限，不给 manage。同时把事项分析从 `events.create` 改成 `anyOf: [ledger.post, events.create]`——**分析产出凭证草稿，那是记账动作**，此前会计（唯一做账的人）反而跑不了它 |

### 4.5 第三批修复：增值税底稿 `NaN`（1 条，但牵动整条申报链路）

这是六份报告里最重的一条——**报给税务局的数字是 `NaN`**。

`tax_items.basis` 一个字段承担了两件类型不同的事：生成侧写**政策依据散文**
（「需结合交付、验收或约定开票条件确认纳税义务发生时点。」），
消费侧当**计税依据金额** `Number(item.basis)`。于是：

```
GET /api/tax/vat-working-paper → {"outputTaxAmount":"NaN","payableVatAmount":"NaN"}
导出的 XML → <本期销项税额>NaN</本期销项税额>
```

而浏览器把这份文件正常下载了。

**为什么此前没被发现**：底稿模块自己的四条单测用 `basis: "1000"` 构造输入——
一个干净的数字字符串，而生产环境写进这个字段的从来都是散文。
**测试喂的输入不是系统真实产生的输入**，所以它们一直是绿的。

修复分五处：

1. **迁移 099**：加 `taxable_amount_cents`（整数分），存量从事项金额回填。
   取不到的保持 `null`——如实记「不知道」，而不是填 0 让它悄悄参与合计
2. **类型**：`TaxItem.taxableAmountCents: number | null` 设为**必填**，
   让 TypeScript 替我找出所有构造 TaxItem 的地方（找出 13 处）
3. **生成侧**：合同收入按**价税分离后的不含税额**给计税依据——
   直接拿含税总额当依据会多算一截税，是实务上最常见的错法之一。
   疑似重复的收入**不给金额**（留 null），它算不算数还没定
4. **消费侧**：底稿读金额列；缺失的行不计入合计，但在
   `incompleteTaxItemIds` 里显式列出，行上标 `basisMissing`，
   `taxableAmount` 为 `null` 而不是 `"0.00"`
5. **两道闸门**：申报导出前检查 `incompleteTaxItemIds`，非空则 409 拒绝导出；
   XML 生成器的 `amt()` 拒绝非有限数并抛错。
   **宁可让导出失败**——失败会让人去补数据，一个格式正常但数字是 NaN
   的文件会被直接上传

顺带修出第三层问题：**会计有权限分析但看不到事项**。V15 把可见性收敛到
「owner + 显式协作人」后，会计对业务部门的事项一律 404，而分析是他的本职。
把 `role-accountant` 加进公司级可见角色——会计是唯一做账的人，
全公司的业务最终都要经他的手变成凭证。这不是把 V15 的收敛退回去：
收敛针对的是普通成员按部门扩散，记账岗位全量可见是岗位职责决定的。

### 4.6 第四批修复：审批流从死代码变成真流程（2 条）

| # | 缺陷 | 根因 | 修复 |
|---|------|------|------|
| 16 | **提交报销从不启动审批流** | `submitForApproval` **全仓只有它自己的测试在调用**。种子里配好的流程 `afl-seed-cmp-v4-tech` 一直在那儿，只是从提交那一刻起就被绕过：`approval_instances` 里没有报销单，「我的审批」对谁都是空的，没有任何人被通知 | 新增 `approval-sync.ts` 把两个方向都接上：提交建实例、批准/驳回推进实例。**只建不推会换一种幽灵**——待办里堆着一批早就处理完的单子 |
| 17 | **三类单据前台没有审批入口** | 申请单/借款单/报销单全部只能「提交」，`pending` 落进一个渲染 `—` 的分支，提交后永久卡住 | 报销单 `pending` 行加「批准/驳回」，判定抽成 `approval-actions.ts` 带单测。**界面不显示 ≠ 点不了**：服务端仍独立校验，两层都要有 |

配套改动：

- `/api/access/me` 增加 `permissions` 字段。前端要按权限决定显示什么按钮，
  此前只有 `roleIds`——前端自己推权限等于把后端权限表复制一份，
  而漂移方向通常是**把不该显示的按钮显示出来**
- 没配审批流时**不阻塞提交**：直接拒绝会让所有还没配流程的公司交不了报销单，
  那是把一次缺陷修复做成一次故障。改为如实提示「本公司没有配审批流，
  这张单会由有审批权限的同事直接处理」

写测试时两次撞到自己的臆想，都按库里的真实配置改了：
种子**本来就配好**了报销审批流（我以为没有），而流程第一级解析出来的
审批人是**会计**（我以为是财务负责人）。

### 4.7 第五批修复：借款单接审批流，堵掉自借自批自付（1 条）

| # | 缺陷 | 根因 | 修复 |
|---|------|------|------|
| 18 | **出纳自借、自批、自付备用金**，同一个人 36 毫秒走完全流程 | 与报销单**完全同形**：`transition` 只由 `expense.submit` 守护（人人都有），`transitionAdvance` 不接收操作人。而打款走的是**另一条独立路径** `POST /api/advances/:id/pay`，同样不看是谁在付 | 归属规则补 `advance`；判定抽成 `access/expense-actions.ts` 与报销共用；**两条路径都拦** |

这条是角色实验里唯一从**真实审计日志**翻出来的缺陷——不是构造出来的，
是出纳 agent 在自己的操作痕迹里发现了 3 组：

```
09:22:09.713 usr-v4-cashier advance.submit  ADV-202608-0001
09:22:09.727 usr-v4-cashier advance.approve ADV-202608-0001
09:22:09.749 usr-v4-cashier advance.pay     ADV-202608-0001
```

**只拦 transition 挡不住**：反向验证时我单独摘掉打款那处拦截，
测试立刻变红——钱照样能付出去。

顺带把两处重复的代码合并：
- `access/expense-actions.ts`：报销与借款共用一套动作权限判定
- `approval/document-sync.ts`：审批同步从报销模块移出并泛化，两类单据共用
  （原 `reimbursements/approval-sync.ts`）

### 4.8 第六批修复：付款闭环打通（1 条，解掉出纳两条阻断）

| # | 缺陷 | 根因 | 修复 |
|---|------|------|------|
| 19 | **银企直连发款与银行 CSV 导出都不可达** | `payments.status = 'submitted'` **全库没有任何路径能产生**——它只被检查、从没被写入，全仓唯一写状态的地方是确认付款写 `paid` | 补 `POST /api/payments/:id/submit`（draft → submitted），前台加「提交待发」按钮 |

这是「后端能做但前台点不到」的一个新变种：**连后端也走不通**，
因为前置状态压根到不了。出纳报的两条阻断都卡在这一个点上：

- 银企直连 `POST /api/bank-connect/instructions` 恒返回 409 `BANK_PAYMENT_NOT_SUBMITTED`
- 导出银行 CSV 的复选框 `disabled: row.status !== "submitted"`，**永远勾不中任何一行**

**门槛本身没错**——「草稿不能发给银行」是对的，草稿的意思就是「还没定」。
缺的是那个动作，而不是该把门槛拆掉。

两个设计决定：

- **不强制所有付款走这一步**：手工付款（现金、柜台转账）仍可 `draft → paid`
  直接确认。强制会破坏那条正当的流程
- 银企直连按钮只对 `submitted` 显示，草稿显示「先提交待发」——
  **摆一个必然 409 的按钮比不摆更糟**

### 4.9 第七批修复：纳税人档案支持沿革（1 条）

| # | 缺陷 | 根因 | 修复 |
|---|------|------|------|
| 20 | **新建纳税人档案会作废全部历史档** | 写入端每次新增无条件把**所有** active 改成 inactive，而读取端 `resolveActiveTaxpayerProfile` 本来就是按「取生效日 ≤ 查询日的最近一条」的多档设计——两端互相矛盾 | 迁移 100 加 `effective_to`；写入端改用**重叠校验**（照搬税率主数据那一套）；读取端认失效日 |

税务专员实测到的场景最能说明严重性：录一条 **2030-01-01 生效**的小规模登记，
当场把 2026 年那条也改成 inactive，`GET /api/tax/rules?occurredOn=2026-05-01`
立刻变成「Active taxpayer profile not found」——**整个税务模块当期瘫痪**，
而用户只是录了一条未来生效的登记。

纳税人身份是**会变的**（小规模转一般纳税人）。重算 2024 年的账要按当时的身份，
和税率沿革（17%→16%→13%）是同一个道理——那一套早就用「生效区间 + 重叠校验」
解决了，这里照搬。

存量回填按生效日排序、前一条封口到后一条生效日的前一天。
**被旧逻辑改成 inactive 的历史档不动**——分不清那是用户主动停用的，
还是被那个 bug 顺手改掉的，猜错方向会凭空改变历史口径。

### 4.10 第八批修复：申请单接审批流，三类单据的自批漏洞全堵上（1 条）

| # | 缺陷 | 根因 | 修复 |
|---|------|------|------|
| 21 | **员工能批准自己 8000 元的采购申请** | 代码里写着「批准/驳回的判权在审批流那一侧，这里不重复判」——而**审批流那一侧从来不存在**（`submitForApproval` 全仓只有测试在调）。一句对的话把一个洞说成了设计 | 在 store 层加「审批人 ≠ 发起人」；接上审批流同步 |

「两处各判一次迟早不一致」本身是句对的话。问题是那一处从没被启用过。

现在审批流真的接上了，**这一层仍然要判**：没配审批流的公司走「由有审批
权限的同事直接处理」那条路，那条路上没有别的东西拦着。
**内控底线不能依赖「另有一处会管」**——尤其当那一处可能根本没被启用。

一个刻意保留的区分：**撤回允许、驳回禁止**。撤回是发起人收回自己的请求
（本人动作），驳回是审批人的决定。两者语义不同，一起拦掉会让人撤不了
自己填错的单。

至此三类费用单据（报销、借款、申请）的自批漏洞全部堵上，共用同一套判定思路。

## 5. 这次实验揭示的更深层问题

### 5.1 我自己刚补的入口，同样是不存在的

V15 我补了凭证红冲入口，提交信息里写着「手册承诺了一个不存在的按钮」。
这次会计角色报告：**那个按钮也不存在**。

```tsx
{!isPosted && (
  …
  {detail.status === "posted" && <红冲按钮 />}   // ← 恒假
)}
```

当时 `tsc` 干净、1025 条单测全绿、前台入口护栏也绿——护栏查的是
「前端源码里有没有出现 `reverseVoucher`」，那个符号确实出现在两个文件里。

**三道防线全绿，按钮却不存在。符号存在 ≠ 按钮可见。**

已修，并补了 `voucher-detail-actions.test.tsx`：逐状态断言「该出现的出现了、
不该出现的没出现」，反向验证过。

### 5.2 前台入口护栏还有第三个洞

- 第一个洞（V15 修）：`/api/events/:id/collaborators` 被砍成 `/api/events` 就算命中
- 第二个洞（董事长发现）：`/api/boss-qa/chat` 的末段 `chat` 被 `/api/assistant/chat` 遮蔽
- 第三个洞（员工发现）：护栏匹配 URL **字符串**，而 API client 文件天然包含所有 URL——
  只要在 `lib/api*.ts` 里定义了函数，哪怕没有任何页面调用它，护栏也是绿的

**一条查「字符串出现过没有」的护栏，永远证明不了「用户点得到」。**

### 5.3 测试沿着最顺的那条路走，缺陷在岔路上

- 无事项凭证过不了账：所有既有凭证测试都从经营事项出发建凭证
- 增值税 NaN：模块单测用 `basis: "1000"`，而生产写进去的是政策散文
- 报销自批：`transitionReimbursement` 的签名里压根没有操作人这个概念，
  针对它的单测再多也只能验证状态机本身

**测试构造的输入不是系统真实产生的输入**——这是同一类病的三个变种。

## 6. 我在这次实验中犯的错

**我清空了正在被使用的数据库。** 写「无事项凭证过账」的集成测试时，
按惯例调了 `resetTestDatabase`，而当时财务负责人 agent 还在运行。

这正是我在作业说明里明令禁止 agent 做的事，也是这一轮**第三次**踩同一个坑
（前两次：集成测试运行期间改代码导致 54 条失败；并发跑同一个库）。

万幸六份报告都在 reset 之前写完，结论没有丢失。但**报告里引用的实验数据全部没了**——
后续要复查任何一条发现，都得重新构造。这个损失是实打实的。

教训不是「下次小心」，而是：**集成测试默认会 reset 数据库，
这件事必须在启动任何共享环境实验之前就摆在明面上。**

## 7. 收口

### 7.1 补一条「真的点页面」的 E2E

八批修复里最贵的两个教训是同一个形状：

1. **红冲按钮是死代码** —— 我补的入口嵌在恒假的条件里
2. **前台无法过账** —— `postVoucher()` 写死空 body

两者的共同点：**所有不打开浏览器的检查都通过了**。
tsc 干净、单测全绿、前台入口护栏也绿（它查的是「源码里有没有出现这个符号」）。

所以补了 `voucher-actions-clickable.spec.ts`：在真实浏览器里点开凭证详情，
断言终审人选择器出现、红冲按钮出现。既有的 `accounting-closed-loop.spec.ts`
走 API 验业务链路，这条走页面只验「按钮在不在」——两条各司其职。

写这条测试时它自己抓出一个真缺陷（见下），也把我三个错误假设逐一暴露：
选凭证靠碰运气（种子里有的用汇总科目，过账会被正确拦下）、
按钮定位没收窄到详情面板（列表每行也有同名按钮）、
让会计一个人走完复核与过账（职责分离在拦我）。

### 7.2 顺带修掉：职责分离的错误文案全是英文

写 E2E 时抓到服务端原样返回
`reviewer and poster must be different users`——**直接弹给用户**。
六条职责分离消息全是英文原文，会计与税务专员在角色实验里都撞到过。

职责分离是这套系统最该讲清楚的规则之一：它拦住你不是因为出错了，
而是因为内控要求换个人来做。这句话必须说明白。六条全部汉化。

### 7.3 一次数据污染的记录

跑完整 E2E 时两条场景测试失败。重置数据库后单独跑，全部通过——
污染来自我**调试新测试时那几轮**点了种子凭证并把它们过账了，
破坏了后面测试的前提。新测试本身只动自己造的数据（两条一起跑验证过）。

这已经是本轮第四次踩共享环境的坑（前三次：集成测试运行期间改代码、
并发跑同一个库、reset 掉正在使用的数据库）。**规律很清楚：
任何在共享库上的手工调试，都要当成会污染后续测试来对待。**
